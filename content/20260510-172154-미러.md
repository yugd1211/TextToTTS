# Mirror Dedicated Server 온보딩 — 오디오북용 대본

## 프롤로그

지금부터, Mirror 데디케이트 서버 온보딩을 시작하겠습니다.

이 오디오북은 Unity 클라이언트 개발자가 Mirror 기반 데디케이트 서버를 만들기 전에, 전체 흐름을 머릿속에 잡을 수 있도록 구성한 입문용 안내서입니다.

여기서 다루는 핵심은 세 가지입니다.

첫 번째, 게임 서버가 무엇을 책임지는가.

두 번째, PUN2와 Mirror는 어떤 관점에서 다른가.

세 번째, TCP, UDP, KCP, 호스팅, 쿠버네티스 같은 단어들을 어떤 순서로 이해해야 하는가.

이 문서는 최종 기술 결정을 내리기 위한 문서가 아닙니다. 지금 단계에서는 “정답을 확정하는 것”보다 “서버 개발의 전체 흐름을 이해하는 것”이 더 중요합니다.

따라서 편하게 들으시면 됩니다. 모든 용어를 처음부터 완벽히 외우려고 하지 않아도 괜찮습니다. 먼저 큰 그림을 잡고, 그다음 실제 프로젝트 코드와 Mirror 샘플을 보면서 하나씩 연결하면 됩니다.

## 1장. 한 줄로 이해하는 PUN2와 Mirror

먼저 가장 중요한 결론부터 말하겠습니다.

PUN2는 Photon이 운영하는 서버 생태계에 클라이언트가 붙는 방식에 가깝습니다.

반면, Mirror와 데디케이트 서버는 우리가 만든 Unity 게임 빌드가 서버 프로세스로 실행되고, 그 서버가 게임 상태를 권위 있게 판단하는 방식에 가깝습니다.

조금 더 쉽게 말해보겠습니다.

PUN2를 사용할 때는 보통 Photon Cloud라는 이미 준비된 네트워크 환경을 사용합니다. 방을 만들고, 플레이어가 들어오고, 네트워크 메시지를 주고받는 기반이 이미 많이 준비되어 있습니다. 그래서 빠르게 멀티플레이를 붙이기에 좋습니다.

하지만 서버 로직을 깊게 제어하고 싶을 때는 제한이 생길 수 있습니다. 예를 들어, 서버가 직접 충돌을 판단하고, 데미지를 계산하고, 유저의 부정한 요청을 검증하는 구조를 만들고 싶다면 관리형 서비스만으로는 답답할 수 있습니다.

반대로 Mirror는 더 직접적입니다.

Unity 프로젝트 안에서 서버 역할을 하는 코드를 작성합니다. 같은 Unity 프로젝트를 클라이언트로도 빌드할 수 있고, 서버 전용 프로세스로도 빌드할 수 있습니다.

이 방식은 자유도가 높습니다. 서버 권위 구조를 직접 만들 수 있고, 게임 상태를 어떻게 검증할지도 직접 결정할 수 있습니다.

하지만 그만큼 책임도 늘어납니다.

서버 빌드를 어떻게 만들지, 서버를 어디에 띄울지, 포트를 어떻게 열지, 클라이언트가 어떤 주소로 접속할지, 매치메이킹은 어떻게 할지, 서버 로그와 재시작은 어떻게 관리할지까지 직접 고민해야 합니다.

즉, PUN2는 빠르게 시작하기 좋은 관리형 네트워크 솔루션에 가깝고, Mirror 데디케이트 서버는 우리가 직접 게임 서버를 운영하는 구조에 가깝습니다.

## 2장. Mirror를 선택하면 생기는 책임

Mirror를 사용해서 데디케이트 서버를 만들겠다는 말은, 단순히 네트워크 라이브러리를 하나 추가한다는 뜻이 아닙니다.

이 말은 프로젝트가 서버 운영의 일부 책임을 직접 가져가겠다는 뜻입니다.

예를 들어 서버 빌드를 만들어야 합니다.

클라이언트 빌드와 서버 빌드는 목적이 다릅니다. 클라이언트 빌드는 유저가 실행하는 게임 앱입니다. 서버 빌드는 유저가 직접 조작하지 않는 서버 프로세스입니다.

서버는 보통 그래픽 화면 없이 실행됩니다. 이런 실행 방식을 흔히 헤드리스라고 부릅니다.

그리고 서버를 실행할 머신도 필요합니다. 처음에는 같은 PC에서 테스트할 수 있습니다. 그 다음에는 로컬 네트워크의 다른 PC에서 테스트할 수 있습니다. 그 다음 단계로 VPS나 클라우드 서버에 올려볼 수 있습니다.

여기서 끝이 아닙니다.

서버가 사용하는 포트를 열어야 합니다. 방화벽이나 클라우드 보안 그룹도 설정해야 합니다. 클라이언트가 서버에 접속할 주소도 알아야 합니다.

운영 단계로 가면 서버가 죽었을 때 어떻게 다시 켤지, 로그는 어디에 남길지, 동시에 몇 명까지 접속 가능한지, 여러 방이 필요할 때 서버 인스턴스를 어떻게 늘릴지도 고민해야 합니다.

그래서 Mirror는 “간단하지 않다”기보다, “직접 다루는 영역이 넓다”고 이해하는 편이 좋습니다.

PUN2가 많은 운영 부담을 Photon 생태계에 맡기는 구조라면, Mirror 데디케이트 서버는 프로젝트가 더 많은 통제권과 책임을 가져오는 구조입니다.

## 3장. Server, Client, Host, Dedicated Server

Mirror를 공부할 때 가장 먼저 익숙해져야 하는 용어가 있습니다.

서버, 클라이언트, 호스트, 데디케이트 서버입니다.

먼저 클라이언트는 플레이어가 실행하는 게임 앱입니다. 우리가 흔히 말하는 게임 클라이언트입니다.

서버는 여러 클라이언트가 접속하는 중심입니다. 서버는 게임 상태를 관리하고, 클라이언트들의 요청을 받아 처리하며, 그 결과를 다시 클라이언트들에게 동기화합니다.

호스트는 조금 특이합니다.

호스트는 하나의 프로세스가 서버 역할과 클라이언트 역할을 동시에 하는 방식입니다. 즉, 내가 플레이하는 게임 안에서 서버도 함께 실행되는 구조입니다.

개발 초기에는 호스트 모드가 매우 편합니다. 서버와 클라이언트가 같은 프로세스에 있기 때문에 테스트가 쉽고, 에디터에서 바로 흐름을 확인할 수 있습니다.

하지만 실제 운영에서 더 명확한 서버 권위 구조를 만들고 싶다면 데디케이트 서버를 고려하게 됩니다.

데디케이트 서버는 플레이어가 조작하지 않는 서버 전용 프로세스입니다. 보통 화면이 없고, 입력도 받지 않으며, 게임 상태 판단과 네트워크 동기화에 집중합니다.

정리하면 이렇습니다.

클라이언트는 유저가 실행하는 게임입니다.

서버는 게임 상태를 관리하는 중심입니다.

호스트는 서버와 클라이언트가 한 프로세스 안에 같이 있는 개발 친화적인 형태입니다.

데디케이트 서버는 서버 역할만 수행하는 전용 프로세스입니다.

처음부터 데디케이트 서버만 붙잡고 시작하면 어렵게 느껴질 수 있습니다. 그래서 권장하는 순서는 이렇습니다.

먼저 에디터에서 호스트와 클라이언트 흐름을 이해합니다.

그 다음 같은 PC에서 서버 전용 인스턴스와 클라이언트 인스턴스를 나눠 테스트합니다.

그 다음 다른 PC나 로컬 네트워크에서 접속을 테스트합니다.

그 다음 Linux 데디케이트 서버 빌드를 만듭니다.

마지막으로 VPS나 클라우드에 올려서 원격 접속을 실험합니다.

이 순서로 가면 서버 개발이 훨씬 덜 막막해집니다.

## 4장. 이 프로젝트에서 먼저 봐야 할 위치

이제 실제 프로젝트 기준으로 어디를 보면 좋을지 이야기해보겠습니다.

현재 프로젝트에는 Mirror 관련 코드와 프로젝트용 Mirror 샘플이 함께 들어 있습니다.

Mirror 자체 패키지나 엔진 코드 쪽에서는 NetworkManager, NetworkRoomManager, KcpTransport 같은 파일을 먼저 보면 좋습니다.

NetworkManager는 Mirror 네트워크 흐름의 중심입니다. 서버를 시작하고, 클라이언트를 시작하고, 호스트를 시작하는 기본 흐름이 이 안에 들어 있습니다.

NetworkRoomManager는 룸 기반 구조를 만들 때 참고할 수 있습니다. 예를 들어 플레이어가 방에 들어오고, 준비 상태가 되고, 일정 조건이 맞으면 게임 씬으로 넘어가는 구조를 이해할 때 도움이 됩니다.

KcpTransport는 실제 네트워크 전송 계층과 관련된 부분입니다. 처음부터 내부 구현을 깊게 파고들 필요는 없지만, Mirror가 어떤 포트와 어떤 전송 방식을 사용하는지 확인할 때 중요합니다.

프로젝트 샘플 쪽에서는 MirrorOffline 씬, MirrorGameRoom 씬, MirrorGamePlay 씬을 순서대로 보는 것이 좋습니다.

MirrorOffline은 메뉴 또는 진입점 역할을 합니다. 여기서 호스트를 시작하거나 클라이언트 접속을 시작하는 흐름을 볼 수 있습니다.

MirrorGameRoom은 게임에 들어가기 전 대기방 역할을 합니다. 룸 플레이어, Ready 상태, 게임 씬으로 넘어가기 전의 흐름을 확인할 수 있습니다.

MirrorGamePlay는 실제 플레이가 이루어지는 씬입니다. 플레이어 프리팹이 생성되고, 이동이나 상태 동기화가 이루어지는 지점을 확인할 수 있습니다.

처음 볼 때는 코드 한 줄 한 줄을 완벽히 이해하려고 하기보다, 이런 질문을 던지면서 보면 좋습니다.

NetworkManager는 어느 GameObject에 붙어 있는가.

Transport는 무엇으로 설정되어 있는가.

Offline Scene과 Online Scene은 무엇으로 설정되어 있는가.

Player Prefab과 Room Player Prefab은 어디를 바라보고 있는가.

Host로 시작했을 때와 Client로 시작했을 때 로그가 어떻게 다른가.

이 질문들에 답할 수 있게 되면 Mirror의 큰 흐름을 잡기 시작한 것입니다.

## 5장. TCP, UDP, KCP를 게임 서버 관점에서 이해하기

이제 네트워크 전송 방식에 대해 이야기해보겠습니다.

게임 서버를 공부하면 TCP, UDP, KCP 같은 단어를 자주 만나게 됩니다.

먼저 TCP입니다.

TCP는 데이터를 안정적으로 보내는 데 강점이 있습니다. 패킷의 순서를 맞춰주고, 중간에 유실된 데이터가 있으면 다시 보내는 방식입니다.

그래서 채팅, 로그인, 상점, 인벤토리 저장처럼 정확성이 중요한 곳에 잘 어울립니다.

하지만 실시간 위치 동기화처럼 최신 상태가 중요한 데이터에는 단점이 생길 수 있습니다. 이전 패킷이 늦게 도착하면, 뒤의 패킷까지 기다리게 되어 지연이 누적될 수 있기 때문입니다.

다음은 UDP입니다.

UDP는 TCP처럼 순서와 재전송을 기본으로 보장하지 않습니다. 대신 가볍고 빠릅니다.

실시간 게임에서는 오래된 위치 정보를 늦게 받는 것보다, 최신 위치 정보를 빨리 받는 것이 더 중요할 때가 많습니다.

예를 들어 플레이어가 이미 앞으로 이동했는데, 늦게 도착한 예전 위치 패킷 때문에 뒤로 순간이동하는 것처럼 보이면 이상합니다.

이런 맥락에서 UDP는 실시간 게임에 자주 사용됩니다.

그 다음은 KCP입니다.

KCP는 UDP 위에서 동작하면서, 신뢰성과 지연 사이의 균형을 잡기 위한 프로토콜 계층으로 이해하면 됩니다.

Mirror에서는 KcpTransport를 사용할 수 있고, 기본 포트로는 흔히 7777번을 사용합니다.

처음 Mirror를 시작할 때는 KCP의 내부 알고리즘을 깊게 외울 필요는 없습니다.

대신 실무적으로는 이런 것들을 확인해야 합니다.

서버가 어떤 포트를 사용하는가.

클라이언트가 어떤 서버 주소로 접속하는가.

방화벽이나 보안 그룹에서 해당 포트가 열려 있는가.

로컬에서는 붙는데 원격에서는 왜 안 붙는가.

서버 로그에 접속과 해제 이벤트가 찍히는가.

이런 질문들을 해결하는 과정에서 TCP, UDP, KCP의 차이가 점점 현실적인 지식으로 연결됩니다.

## 6장. Mirror 데디케이트 서버 튜토리얼 흐름

이제 실제로 어떤 순서로 실험하면 좋은지 살펴보겠습니다.

처음 목표는 완성된 매치메이킹 서버가 아닙니다.

처음 목표는 아주 작게 잡아야 합니다.

첫 번째, 서버 프로세스가 켜진다.

두 번째, 클라이언트가 서버에 붙는다.

세 번째, 플레이어 오브젝트나 간단한 상태가 동기화된다.

이 세 가지만 성공해도 첫 단계는 충분히 의미 있습니다.

첫 번째 단계는 샘플 씬을 이해하는 것입니다.

MirrorOffline 씬에서는 메뉴와 진입 흐름을 봅니다. Host 버튼이나 Client 버튼을 눌렀을 때 어떤 함수가 호출되는지 확인합니다.

MirrorGameRoom 씬에서는 룸 플레이어와 Ready 상태를 봅니다. 플레이어들이 준비되었을 때 어떤 조건으로 게임 씬으로 넘어가는지 확인합니다.

MirrorGamePlay 씬에서는 실제 플레이어 프리팹이 생성되고 상태가 동기화되는 흐름을 봅니다.

두 번째 단계는 Host 모드로 먼저 성공시키는 것입니다.

Host 모드는 서버와 클라이언트가 같은 프로세스 안에서 함께 실행되기 때문에 디버깅이 쉽습니다.

일단 Host를 시작합니다. 그 다음 같은 에디터나 별도 클라이언트 빌드에서 접속합니다. 룸에 진입하고, Ready 상태가 되고, 게임 씬으로 넘어가고, 플레이어가 생성되는지 확인합니다.

세 번째 단계는 ServerOnly 모드입니다.

이제 서버만 켜고, 별도 클라이언트가 접속하는 구조를 실험합니다.

같은 PC에서 테스트할 때는 localhost로 접속할 수 있습니다.

다른 PC나 VPS에서 테스트할 때는 실제 IP 주소나 도메인을 사용해야 합니다.

이 단계에서 중요한 것은 서버 화면이 예쁘게 보이는지가 아닙니다.

중요한 것은 로그와 네트워크 상태를 통해 서버가 살아 있는지 확인하는 것입니다.

네 번째 단계는 데디케이트 서버 빌드를 만드는 것입니다.

Unity에서는 서버 전용 빌드를 만들 수 있습니다. 커맨드라인 빌드에서는 서버 빌드용 옵션을 사용할 수 있습니다.

실제 프로젝트에서는 CI 환경과 빌드 스크립트에 맞춰 서버 빌드 메서드를 따로 만들어두는 것이 좋습니다.

다섯 번째 단계는 로컬에서 서버 빌드를 실행하는 것입니다.

서버 빌드가 만들어졌다면 바로 클라우드에 올리기보다, 먼저 로컬에서 실행해봐야 합니다.

프로세스가 바로 종료되지 않는지 확인합니다.

서버 자동 시작 설정이 되어 있는지 확인합니다.

포트가 열렸는지 확인합니다.

클라이언트가 localhost나 LAN IP로 붙는지 확인합니다.

서버 로그에 접속 이벤트가 찍히는지도 확인합니다.

여섯 번째 단계는 VPS나 클라우드에 올리는 것입니다.

처음부터 쿠버네티스로 가지 않아도 됩니다. 오히려 처음에는 VPS 한 대가 더 좋습니다.

Linux 서버를 준비합니다. 서버 빌드를 업로드합니다. 실행 권한을 줍니다. 포트를 엽니다. 서버를 실행합니다. 클라이언트에서 공인 IP로 접속합니다. 그리고 로그를 확인합니다.

이 단계에서 실패한다면 원인은 대체로 비슷합니다.

포트가 막혀 있거나, 클라이언트 주소가 잘못되었거나, 서버가 자동 시작되지 않았거나, 빌드에 필요한 씬이 빠졌거나, Linux 실행 권한이 없거나, 클라우드 방화벽 설정이 누락된 경우가 많습니다.

일곱 번째 단계는 컨테이너와 쿠버네티스입니다.

하지만 이 단계는 나중입니다.

쿠버네티스는 서버를 잘 만드는 방법이 아닙니다. 이미 서버가 잘 실행될 때, 여러 서버 인스턴스를 배포하고, 스케일하고, 복구하는 운영 도구에 가깝습니다.

그래서 순서는 명확합니다.

먼저 로컬 ServerOnly를 성공시킵니다.

그 다음 Linux 데디케이트 서버 빌드를 성공시킵니다.

그 다음 VPS에서 수동 실행을 성공시킵니다.

그 다음 Docker 이미지화를 생각합니다.

그리고 정말 여러 서버 인스턴스를 관리해야 할 필요가 생겼을 때, 쿠버네티스나 게임 서버 오케스트레이션을 검토합니다.

처음 2주 학습 단계에서는 쿠버네티스보다 서버 빌드가 켜지고 클라이언트가 붙는 것이 훨씬 중요합니다.

## 7장. 서버 권위 로직을 어디에 둘 것인가

Mirror를 쓰는 중요한 이유 중 하나는 서버 권위 구조를 만들기 위해서입니다.

서버 권위란, 최종 판단을 클라이언트가 아니라 서버가 한다는 뜻입니다.

나쁜 구조부터 생각해보겠습니다.

클라이언트가 “나 데미지 100 줬어”라고 말하면 서버가 그대로 믿습니다.

클라이언트가 “나 이 위치로 이동했어”라고 말하면 서버가 그대로 반영합니다.

클라이언트가 “나 아이템 먹었어”라고 말하면 서버가 그대로 인정합니다.

이런 구조는 만들기는 쉽지만, 치트나 조작에 취약합니다.

좋은 구조는 다릅니다.

클라이언트는 입력이나 요청만 보냅니다.

예를 들어 “나는 오른쪽으로 이동하고 싶다”, “나는 공격 버튼을 눌렀다”, “나는 이 아이템을 먹으려고 한다” 정도만 서버에 전달합니다.

서버는 그 요청이 가능한지 검증합니다.

정말 그 위치로 이동할 수 있는지, 공격 범위 안에 적이 있는지, 아이템이 아직 존재하는지, 이미 다른 플레이어가 먹은 것은 아닌지 판단합니다.

그리고 서버가 최종 결과를 결정합니다.

그 결과가 클라이언트들에게 동기화됩니다.

이런 구조가 서버 권위 구조입니다.

처음부터 완벽한 예측 보정이나 롤백까지 구현할 필요는 없습니다.

최소 실험은 아주 단순하게 시작하면 됩니다.

클라이언트가 이동 입력을 보냅니다.

서버가 이동 가능 여부를 판단합니다.

서버가 최종 위치를 갱신합니다.

클라이언트들은 서버가 정한 위치를 받아서 표시합니다.

이 정도만 구현해도 Mirror를 쓰는 이유와 서버 권위의 감각을 잡을 수 있습니다.

## 8장. 최소 실험 체크리스트를 말로 풀어보기

이제 어떤 것들을 확인해야 하는지 체크리스트를 말로 풀어보겠습니다.

먼저 로컬 Host 체크입니다.

MirrorOffline 씬에서 Host 시작이 가능해야 합니다.

룸이나 게임 씬으로 이동할 수 있어야 합니다.

플레이어 프리팹이 생성되는지 확인해야 합니다.

콘솔에 Mirror 관련 오류가 없는지도 확인해야 합니다.

다음은 로컬 ServerOnly와 Client 체크입니다.

서버 인스턴스가 서버 모드로 시작되어야 합니다.

클라이언트가 localhost로 접속할 수 있어야 합니다.

접속과 해제 로그가 찍혀야 합니다.

플레이어 생성이나 간단한 상태 동기화가 확인되어야 합니다.

그 다음은 데디케이트 서버 빌드 체크입니다.

서버 빌드 타겟을 사용해야 합니다.

필요한 씬이 Build Settings에 포함되어 있어야 합니다.

서버 빌드를 실행했을 때 자동으로 서버가 시작되어야 합니다.

설정한 포트, 예를 들어 7777번 포트가 열려 있어야 합니다.

클라이언트가 서버 IP로 접속할 수 있어야 합니다.

마지막은 운영 실험 체크입니다.

VPS나 클라우드 방화벽에서 인바운드 포트를 열어야 합니다.

서버 로그를 확인할 수 있어야 합니다.

서버 재시작 방법이 있어야 합니다.

클라이언트와 서버의 빌드 버전이 맞아야 합니다.

그리고 작게라도 동시 접속 수를 측정해봐야 합니다.

이 체크리스트는 단순해 보이지만, 실제 서버 개발의 대부분은 이런 기본 확인을 정확히 하는 데서 출발합니다.

## 9장. 지금 당장 만들면 좋은 학습 산출물

처음부터 완성 서버를 만들려고 하면 범위가 너무 커집니다.

대신 학습 산출물을 작게 나누면 좋습니다.

첫 번째 산출물은 Mirror 샘플 실행 노트입니다.

어떤 씬에서 어떤 버튼을 누르면 어떤 상태가 되는지 기록합니다.

두 번째 산출물은 Host와 Client 로그 비교표입니다.

Host, ServerOnly, ClientOnly에서 각각 어떤 로그가 찍히는지 비교합니다.

세 번째 산출물은 서버 권위 미니 테스트입니다.

예를 들어 점수나 데미지를 서버에서만 바꿀 수 있게 만들어봅니다.

네 번째 산출물은 데디케이트 서버 빌드 스크립트 초안입니다.

Linux64 서버 빌드를 자동화하는 스크립트를 만들어봅니다.

다섯 번째 산출물은 VPS 접속 실험 기록입니다.

IP, 포트, 방화벽 설정, 접속 성공 여부, 실패 원인을 기록합니다.

여섯 번째 산출물은 운영 방향 결정 문서입니다.

매치메이킹을 직접 만들지, Edgegap이나 Multiplay 같은 호스팅을 쓸지, 혹은 다른 방식을 선택할지 정리합니다.

이 산출물들은 단순한 공부 기록이 아닙니다.

나중에 포트폴리오나 기술 문서로도 이어질 수 있습니다.

특히 게임 클라이언트 개발자 입장에서는 “서버를 직접 다뤄본 경험”을 구조적으로 설명하는 좋은 자료가 됩니다.

## 10장. 2주 학습 로드맵

이제 2주 동안 어떤 순서로 학습하면 좋을지 정리해보겠습니다.

1일차에는 용어를 정리합니다.

Server, Client, Host, Dedicated Server를 이해합니다.

Authority, Spawn, SyncVar, Command, ClientRpc 같은 Mirror 핵심 용어도 가볍게 정리합니다.

Transport, Port, Address 같은 네트워크 기본 용어도 함께 봅니다.

2일차와 3일차에는 Mirror 샘플을 실행합니다.

Host를 실행해보고, Client를 접속시켜봅니다.

Room 흐름을 확인하고, GamePlay 씬에서 동기화가 어떻게 되는지 봅니다.

4일차와 5일차에는 서버 권위 미니 기능을 만들어봅니다.

서버가 점수를 관리하게 하거나, 클라이언트 요청을 검증하고, 잘못된 요청을 무시하는 구조를 실험합니다.

6일차와 7일차에는 ServerOnly 흐름을 실험합니다.

서버 인스턴스와 클라이언트 인스턴스를 분리합니다.

로그를 기준으로 상태를 확인합니다.

포트와 주소 문제를 직접 해결해봅니다.

8일차부터 10일차까지는 데디케이트 서버 빌드를 만듭니다.

Linux 서버 빌드를 만들고, 로컬에서 실행하고, 클라이언트가 접속할 수 있는지 확인합니다.

11일차부터 14일차까지는 원격 서버 실험을 합니다.

VPS에 배포해보고, 방화벽과 포트를 설정하고, 클라이언트에서 공인 IP로 접속해봅니다.

서버 재시작 방법과 로그 확인 방법도 같이 정리합니다.

그리고 마지막으로 Docker나 쿠버네티스가 지금 당장 필요한지 판단합니다.

대부분의 경우, 처음 2주 동안은 쿠버네티스를 깊게 공부하기보다, 서버 빌드와 원격 접속을 성공시키는 것이 훨씬 중요합니다.

## 11장. 최종 판단 기준

이 문서는 최종 아키텍처 결정 문서가 아닙니다.

지금 단계에서의 정답은 명확합니다.

먼저 Mirror 샘플을 실행해서 Host, Client, ServerOnly의 차이를 몸으로 확인해야 합니다.

데디케이트 서버는 Unity 서버 빌드 타겟과 Mirror의 headless start 설정이 맞아야 제대로 동작합니다.

KCP, 포트, 방화벽은 실제 접속 실패를 해결할 때 반드시 이해해야 합니다.

쿠버네티스는 초기 학습 주제가 아닙니다. 서버 빌드와 수동 배포가 성공한 뒤에 생각할 운영 주제입니다.

그리고 PUN2보다 Mirror가 더 직접 다루는 구조라는 점을 기억해야 합니다.

Mirror를 선택한다는 것은 서버 권위 로직과 운영 책임을 프로젝트가 더 많이 가져간다는 뜻입니다.

## 에필로그

정리하겠습니다.

PUN2는 빠르게 멀티플레이를 붙이기 좋은 관리형 네트워크 솔루션에 가깝습니다.

Mirror 데디케이트 서버는 우리가 만든 Unity 서버 프로세스가 게임 상태를 직접 판단하는 구조에 가깝습니다.

이 구조는 자유도가 높고 서버 권위를 만들기 좋습니다.

하지만 서버 빌드, 포트, 방화벽, 호스팅, 로그, 재시작, 매치메이킹 같은 운영 책임도 함께 따라옵니다.

그래서 처음에는 작게 시작해야 합니다.

Host 모드로 성공합니다.

ServerOnly와 Client를 분리합니다.

로컬 서버 빌드를 실행합니다.

VPS에 올려봅니다.

그 다음 Docker나 쿠버네티스를 검토합니다.

가장 중요한 것은 처음부터 완성된 서버를 만들려고 하지 않는 것입니다.

서버가 켜진다.

클라이언트가 붙는다.

상태가 동기화된다.

이 세 가지를 먼저 성공시키는 것이 Mirror 데디케이트 서버 학습의 출발점입니다.

이상으로 Mirror 데디케이트 서버 온보딩을 마치겠습니다.

## 프롤로그

지금부터, Mirror 데디케이트 서버 온보딩을 시작하겠습니다.

이 오디오북은 Unity 클라이언트 개발자가 Mirror 기반 데디케이트 서버를 만들기 전에, 전체 흐름을 머릿속에 잡을 수 있도록 구성한 입문용 안내서입니다.

여기서 다루는 핵심은 세 가지입니다.

첫 번째, 게임 서버가 무엇을 책임지는가.

두 번째, PUN2와 Mirror는 어떤 관점에서 다른가.

세 번째, TCP, UDP, KCP, 호스팅, 쿠버네티스 같은 단어들을 어떤 순서로 이해해야 하는가.

이 문서는 최종 기술 결정을 내리기 위한 문서가 아닙니다. 지금 단계에서는 “정답을 확정하는 것”보다 “서버 개발의 전체 흐름을 이해하는 것”이 더 중요합니다.

따라서 편하게 들으시면 됩니다. 모든 용어를 처음부터 완벽히 외우려고 하지 않아도 괜찮습니다. 먼저 큰 그림을 잡고, 그다음 실제 프로젝트 코드와 Mirror 샘플을 보면서 하나씩 연결하면 됩니다.

## 1장. 한 줄로 이해하는 PUN2와 Mirror

먼저 가장 중요한 결론부터 말하겠습니다.

PUN2는 Photon이 운영하는 서버 생태계에 클라이언트가 붙는 방식에 가깝습니다.

반면, Mirror와 데디케이트 서버는 우리가 만든 Unity 게임 빌드가 서버 프로세스로 실행되고, 그 서버가 게임 상태를 권위 있게 판단하는 방식에 가깝습니다.

조금 더 쉽게 말해보겠습니다.

PUN2를 사용할 때는 보통 Photon Cloud라는 이미 준비된 네트워크 환경을 사용합니다. 방을 만들고, 플레이어가 들어오고, 네트워크 메시지를 주고받는 기반이 이미 많이 준비되어 있습니다. 그래서 빠르게 멀티플레이를 붙이기에 좋습니다.

하지만 서버 로직을 깊게 제어하고 싶을 때는 제한이 생길 수 있습니다. 예를 들어, 서버가 직접 충돌을 판단하고, 데미지를 계산하고, 유저의 부정한 요청을 검증하는 구조를 만들고 싶다면 관리형 서비스만으로는 답답할 수 있습니다.

반대로 Mirror는 더 직접적입니다.

Unity 프로젝트 안에서 서버 역할을 하는 코드를 작성합니다. 같은 Unity 프로젝트를 클라이언트로도 빌드할 수 있고, 서버 전용 프로세스로도 빌드할 수 있습니다.

이 방식은 자유도가 높습니다. 서버 권위 구조를 직접 만들 수 있고, 게임 상태를 어떻게 검증할지도 직접 결정할 수 있습니다.

하지만 그만큼 책임도 늘어납니다.

서버 빌드를 어떻게 만들지, 서버를 어디에 띄울지, 포트를 어떻게 열지, 클라이언트가 어떤 주소로 접속할지, 매치메이킹은 어떻게 할지, 서버 로그와 재시작은 어떻게 관리할지까지 직접 고민해야 합니다.

즉, PUN2는 빠르게 시작하기 좋은 관리형 네트워크 솔루션에 가깝고, Mirror 데디케이트 서버는 우리가 직접 게임 서버를 운영하는 구조에 가깝습니다.

## 2장. Mirror를 선택하면 생기는 책임

Mirror를 사용해서 데디케이트 서버를 만들겠다는 말은, 단순히 네트워크 라이브러리를 하나 추가한다는 뜻이 아닙니다.

이 말은 프로젝트가 서버 운영의 일부 책임을 직접 가져가겠다는 뜻입니다.

예를 들어 서버 빌드를 만들어야 합니다.

클라이언트 빌드와 서버 빌드는 목적이 다릅니다. 클라이언트 빌드는 유저가 실행하는 게임 앱입니다. 서버 빌드는 유저가 직접 조작하지 않는 서버 프로세스입니다.

서버는 보통 그래픽 화면 없이 실행됩니다. 이런 실행 방식을 흔히 헤드리스라고 부릅니다.

그리고 서버를 실행할 머신도 필요합니다. 처음에는 같은 PC에서 테스트할 수 있습니다. 그 다음에는 로컬 네트워크의 다른 PC에서 테스트할 수 있습니다. 그 다음 단계로 VPS나 클라우드 서버에 올려볼 수 있습니다.

여기서 끝이 아닙니다.

서버가 사용하는 포트를 열어야 합니다. 방화벽이나 클라우드 보안 그룹도 설정해야 합니다. 클라이언트가 서버에 접속할 주소도 알아야 합니다.

운영 단계로 가면 서버가 죽었을 때 어떻게 다시 켤지, 로그는 어디에 남길지, 동시에 몇 명까지 접속 가능한지, 여러 방이 필요할 때 서버 인스턴스를 어떻게 늘릴지도 고민해야 합니다.

그래서 Mirror는 “간단하지 않다”기보다, “직접 다루는 영역이 넓다”고 이해하는 편이 좋습니다.

PUN2가 많은 운영 부담을 Photon 생태계에 맡기는 구조라면, Mirror 데디케이트 서버는 프로젝트가 더 많은 통제권과 책임을 가져오는 구조입니다.

## 3장. Server, Client, Host, Dedicated Server

Mirror를 공부할 때 가장 먼저 익숙해져야 하는 용어가 있습니다.

서버, 클라이언트, 호스트, 데디케이트 서버입니다.

먼저 클라이언트는 플레이어가 실행하는 게임 앱입니다. 우리가 흔히 말하는 게임 클라이언트입니다.

서버는 여러 클라이언트가 접속하는 중심입니다. 서버는 게임 상태를 관리하고, 클라이언트들의 요청을 받아 처리하며, 그 결과를 다시 클라이언트들에게 동기화합니다.

호스트는 조금 특이합니다.

호스트는 하나의 프로세스가 서버 역할과 클라이언트 역할을 동시에 하는 방식입니다. 즉, 내가 플레이하는 게임 안에서 서버도 함께 실행되는 구조입니다.

개발 초기에는 호스트 모드가 매우 편합니다. 서버와 클라이언트가 같은 프로세스에 있기 때문에 테스트가 쉽고, 에디터에서 바로 흐름을 확인할 수 있습니다.

하지만 실제 운영에서 더 명확한 서버 권위 구조를 만들고 싶다면 데디케이트 서버를 고려하게 됩니다.

데디케이트 서버는 플레이어가 조작하지 않는 서버 전용 프로세스입니다. 보통 화면이 없고, 입력도 받지 않으며, 게임 상태 판단과 네트워크 동기화에 집중합니다.

정리하면 이렇습니다.

클라이언트는 유저가 실행하는 게임입니다.

서버는 게임 상태를 관리하는 중심입니다.

호스트는 서버와 클라이언트가 한 프로세스 안에 같이 있는 개발 친화적인 형태입니다.

데디케이트 서버는 서버 역할만 수행하는 전용 프로세스입니다.

처음부터 데디케이트 서버만 붙잡고 시작하면 어렵게 느껴질 수 있습니다. 그래서 권장하는 순서는 이렇습니다.

먼저 에디터에서 호스트와 클라이언트 흐름을 이해합니다.

그 다음 같은 PC에서 서버 전용 인스턴스와 클라이언트 인스턴스를 나눠 테스트합니다.

그 다음 다른 PC나 로컬 네트워크에서 접속을 테스트합니다.

그 다음 Linux 데디케이트 서버 빌드를 만듭니다.

마지막으로 VPS나 클라우드에 올려서 원격 접속을 실험합니다.

이 순서로 가면 서버 개발이 훨씬 덜 막막해집니다.

## 4장. 이 프로젝트에서 먼저 봐야 할 위치

이제 실제 프로젝트 기준으로 어디를 보면 좋을지 이야기해보겠습니다.

현재 프로젝트에는 Mirror 관련 코드와 프로젝트용 Mirror 샘플이 함께 들어 있습니다.

Mirror 자체 패키지나 엔진 코드 쪽에서는 NetworkManager, NetworkRoomManager, KcpTransport 같은 파일을 먼저 보면 좋습니다.

NetworkManager는 Mirror 네트워크 흐름의 중심입니다. 서버를 시작하고, 클라이언트를 시작하고, 호스트를 시작하는 기본 흐름이 이 안에 들어 있습니다.

NetworkRoomManager는 룸 기반 구조를 만들 때 참고할 수 있습니다. 예를 들어 플레이어가 방에 들어오고, 준비 상태가 되고, 일정 조건이 맞으면 게임 씬으로 넘어가는 구조를 이해할 때 도움이 됩니다.

KcpTransport는 실제 네트워크 전송 계층과 관련된 부분입니다. 처음부터 내부 구현을 깊게 파고들 필요는 없지만, Mirror가 어떤 포트와 어떤 전송 방식을 사용하는지 확인할 때 중요합니다.

프로젝트 샘플 쪽에서는 MirrorOffline 씬, MirrorGameRoom 씬, MirrorGamePlay 씬을 순서대로 보는 것이 좋습니다.

MirrorOffline은 메뉴 또는 진입점 역할을 합니다. 여기서 호스트를 시작하거나 클라이언트 접속을 시작하는 흐름을 볼 수 있습니다.

MirrorGameRoom은 게임에 들어가기 전 대기방 역할을 합니다. 룸 플레이어, Ready 상태, 게임 씬으로 넘어가기 전의 흐름을 확인할 수 있습니다.

MirrorGamePlay는 실제 플레이가 이루어지는 씬입니다. 플레이어 프리팹이 생성되고, 이동이나 상태 동기화가 이루어지는 지점을 확인할 수 있습니다.

처음 볼 때는 코드 한 줄 한 줄을 완벽히 이해하려고 하기보다, 이런 질문을 던지면서 보면 좋습니다.

NetworkManager는 어느 GameObject에 붙어 있는가.

Transport는 무엇으로 설정되어 있는가.

Offline Scene과 Online Scene은 무엇으로 설정되어 있는가.

Player Prefab과 Room Player Prefab은 어디를 바라보고 있는가.

Host로 시작했을 때와 Client로 시작했을 때 로그가 어떻게 다른가.

이 질문들에 답할 수 있게 되면 Mirror의 큰 흐름을 잡기 시작한 것입니다.

## 5장. TCP, UDP, KCP를 게임 서버 관점에서 이해하기

이제 네트워크 전송 방식에 대해 이야기해보겠습니다.

게임 서버를 공부하면 TCP, UDP, KCP 같은 단어를 자주 만나게 됩니다.

먼저 TCP입니다.

TCP는 데이터를 안정적으로 보내는 데 강점이 있습니다. 패킷의 순서를 맞춰주고, 중간에 유실된 데이터가 있으면 다시 보내는 방식입니다.

그래서 채팅, 로그인, 상점, 인벤토리 저장처럼 정확성이 중요한 곳에 잘 어울립니다.

하지만 실시간 위치 동기화처럼 최신 상태가 중요한 데이터에는 단점이 생길 수 있습니다. 이전 패킷이 늦게 도착하면, 뒤의 패킷까지 기다리게 되어 지연이 누적될 수 있기 때문입니다.

다음은 UDP입니다.

UDP는 TCP처럼 순서와 재전송을 기본으로 보장하지 않습니다. 대신 가볍고 빠릅니다.

실시간 게임에서는 오래된 위치 정보를 늦게 받는 것보다, 최신 위치 정보를 빨리 받는 것이 더 중요할 때가 많습니다.

예를 들어 플레이어가 이미 앞으로 이동했는데, 늦게 도착한 예전 위치 패킷 때문에 뒤로 순간이동하는 것처럼 보이면 이상합니다.

이런 맥락에서 UDP는 실시간 게임에 자주 사용됩니다.

그 다음은 KCP입니다.

KCP는 UDP 위에서 동작하면서, 신뢰성과 지연 사이의 균형을 잡기 위한 프로토콜 계층으로 이해하면 됩니다.

Mirror에서는 KcpTransport를 사용할 수 있고, 기본 포트로는 흔히 7777번을 사용합니다.

처음 Mirror를 시작할 때는 KCP의 내부 알고리즘을 깊게 외울 필요는 없습니다.

대신 실무적으로는 이런 것들을 확인해야 합니다.

서버가 어떤 포트를 사용하는가.

클라이언트가 어떤 서버 주소로 접속하는가.

방화벽이나 보안 그룹에서 해당 포트가 열려 있는가.

로컬에서는 붙는데 원격에서는 왜 안 붙는가.

서버 로그에 접속과 해제 이벤트가 찍히는가.

이런 질문들을 해결하는 과정에서 TCP, UDP, KCP의 차이가 점점 현실적인 지식으로 연결됩니다.

## 6장. Mirror 데디케이트 서버 튜토리얼 흐름

이제 실제로 어떤 순서로 실험하면 좋은지 살펴보겠습니다.

처음 목표는 완성된 매치메이킹 서버가 아닙니다.

처음 목표는 아주 작게 잡아야 합니다.

첫 번째, 서버 프로세스가 켜진다.

두 번째, 클라이언트가 서버에 붙는다.

세 번째, 플레이어 오브젝트나 간단한 상태가 동기화된다.

이 세 가지만 성공해도 첫 단계는 충분히 의미 있습니다.

첫 번째 단계는 샘플 씬을 이해하는 것입니다.

MirrorOffline 씬에서는 메뉴와 진입 흐름을 봅니다. Host 버튼이나 Client 버튼을 눌렀을 때 어떤 함수가 호출되는지 확인합니다.

MirrorGameRoom 씬에서는 룸 플레이어와 Ready 상태를 봅니다. 플레이어들이 준비되었을 때 어떤 조건으로 게임 씬으로 넘어가는지 확인합니다.

MirrorGamePlay 씬에서는 실제 플레이어 프리팹이 생성되고 상태가 동기화되는 흐름을 봅니다.

두 번째 단계는 Host 모드로 먼저 성공시키는 것입니다.

Host 모드는 서버와 클라이언트가 같은 프로세스 안에서 함께 실행되기 때문에 디버깅이 쉽습니다.

일단 Host를 시작합니다. 그 다음 같은 에디터나 별도 클라이언트 빌드에서 접속합니다. 룸에 진입하고, Ready 상태가 되고, 게임 씬으로 넘어가고, 플레이어가 생성되는지 확인합니다.

세 번째 단계는 ServerOnly 모드입니다.

이제 서버만 켜고, 별도 클라이언트가 접속하는 구조를 실험합니다.

같은 PC에서 테스트할 때는 localhost로 접속할 수 있습니다.

다른 PC나 VPS에서 테스트할 때는 실제 IP 주소나 도메인을 사용해야 합니다.

이 단계에서 중요한 것은 서버 화면이 예쁘게 보이는지가 아닙니다.

중요한 것은 로그와 네트워크 상태를 통해 서버가 살아 있는지 확인하는 것입니다.

네 번째 단계는 데디케이트 서버 빌드를 만드는 것입니다.

Unity에서는 서버 전용 빌드를 만들 수 있습니다. 커맨드라인 빌드에서는 서버 빌드용 옵션을 사용할 수 있습니다.

실제 프로젝트에서는 CI 환경과 빌드 스크립트에 맞춰 서버 빌드 메서드를 따로 만들어두는 것이 좋습니다.

다섯 번째 단계는 로컬에서 서버 빌드를 실행하는 것입니다.

서버 빌드가 만들어졌다면 바로 클라우드에 올리기보다, 먼저 로컬에서 실행해봐야 합니다.

프로세스가 바로 종료되지 않는지 확인합니다.

서버 자동 시작 설정이 되어 있는지 확인합니다.

포트가 열렸는지 확인합니다.

클라이언트가 localhost나 LAN IP로 붙는지 확인합니다.

서버 로그에 접속 이벤트가 찍히는지도 확인합니다.

여섯 번째 단계는 VPS나 클라우드에 올리는 것입니다.

처음부터 쿠버네티스로 가지 않아도 됩니다. 오히려 처음에는 VPS 한 대가 더 좋습니다.

Linux 서버를 준비합니다. 서버 빌드를 업로드합니다. 실행 권한을 줍니다. 포트를 엽니다. 서버를 실행합니다. 클라이언트에서 공인 IP로 접속합니다. 그리고 로그를 확인합니다.

이 단계에서 실패한다면 원인은 대체로 비슷합니다.

포트가 막혀 있거나, 클라이언트 주소가 잘못되었거나, 서버가 자동 시작되지 않았거나, 빌드에 필요한 씬이 빠졌거나, Linux 실행 권한이 없거나, 클라우드 방화벽 설정이 누락된 경우가 많습니다.

일곱 번째 단계는 컨테이너와 쿠버네티스입니다.

하지만 이 단계는 나중입니다.

쿠버네티스는 서버를 잘 만드는 방법이 아닙니다. 이미 서버가 잘 실행될 때, 여러 서버 인스턴스를 배포하고, 스케일하고, 복구하는 운영 도구에 가깝습니다.

그래서 순서는 명확합니다.

먼저 로컬 ServerOnly를 성공시킵니다.

그 다음 Linux 데디케이트 서버 빌드를 성공시킵니다.

그 다음 VPS에서 수동 실행을 성공시킵니다.

그 다음 Docker 이미지화를 생각합니다.

그리고 정말 여러 서버 인스턴스를 관리해야 할 필요가 생겼을 때, 쿠버네티스나 게임 서버 오케스트레이션을 검토합니다.

처음 2주 학습 단계에서는 쿠버네티스보다 서버 빌드가 켜지고 클라이언트가 붙는 것이 훨씬 중요합니다.

## 7장. 서버 권위 로직을 어디에 둘 것인가

Mirror를 쓰는 중요한 이유 중 하나는 서버 권위 구조를 만들기 위해서입니다.

서버 권위란, 최종 판단을 클라이언트가 아니라 서버가 한다는 뜻입니다.

나쁜 구조부터 생각해보겠습니다.

클라이언트가 “나 데미지 100 줬어”라고 말하면 서버가 그대로 믿습니다.

클라이언트가 “나 이 위치로 이동했어”라고 말하면 서버가 그대로 반영합니다.

클라이언트가 “나 아이템 먹었어”라고 말하면 서버가 그대로 인정합니다.

이런 구조는 만들기는 쉽지만, 치트나 조작에 취약합니다.

좋은 구조는 다릅니다.

클라이언트는 입력이나 요청만 보냅니다.

예를 들어 “나는 오른쪽으로 이동하고 싶다”, “나는 공격 버튼을 눌렀다”, “나는 이 아이템을 먹으려고 한다” 정도만 서버에 전달합니다.

서버는 그 요청이 가능한지 검증합니다.

정말 그 위치로 이동할 수 있는지, 공격 범위 안에 적이 있는지, 아이템이 아직 존재하는지, 이미 다른 플레이어가 먹은 것은 아닌지 판단합니다.

그리고 서버가 최종 결과를 결정합니다.

그 결과가 클라이언트들에게 동기화됩니다.

이런 구조가 서버 권위 구조입니다.

처음부터 완벽한 예측 보정이나 롤백까지 구현할 필요는 없습니다.

최소 실험은 아주 단순하게 시작하면 됩니다.

클라이언트가 이동 입력을 보냅니다.

서버가 이동 가능 여부를 판단합니다.

서버가 최종 위치를 갱신합니다.

클라이언트들은 서버가 정한 위치를 받아서 표시합니다.

이 정도만 구현해도 Mirror를 쓰는 이유와 서버 권위의 감각을 잡을 수 있습니다.

## 8장. 최소 실험 체크리스트를 말로 풀어보기

이제 어떤 것들을 확인해야 하는지 체크리스트를 말로 풀어보겠습니다.

먼저 로컬 Host 체크입니다.

MirrorOffline 씬에서 Host 시작이 가능해야 합니다.

룸이나 게임 씬으로 이동할 수 있어야 합니다.

플레이어 프리팹이 생성되는지 확인해야 합니다.

콘솔에 Mirror 관련 오류가 없는지도 확인해야 합니다.

다음은 로컬 ServerOnly와 Client 체크입니다.

서버 인스턴스가 서버 모드로 시작되어야 합니다.

클라이언트가 localhost로 접속할 수 있어야 합니다.

접속과 해제 로그가 찍혀야 합니다.

플레이어 생성이나 간단한 상태 동기화가 확인되어야 합니다.

그 다음은 데디케이트 서버 빌드 체크입니다.

서버 빌드 타겟을 사용해야 합니다.

필요한 씬이 Build Settings에 포함되어 있어야 합니다.

서버 빌드를 실행했을 때 자동으로 서버가 시작되어야 합니다.

설정한 포트, 예를 들어 7777번 포트가 열려 있어야 합니다.

클라이언트가 서버 IP로 접속할 수 있어야 합니다.

마지막은 운영 실험 체크입니다.

VPS나 클라우드 방화벽에서 인바운드 포트를 열어야 합니다.

서버 로그를 확인할 수 있어야 합니다.

서버 재시작 방법이 있어야 합니다.

클라이언트와 서버의 빌드 버전이 맞아야 합니다.

그리고 작게라도 동시 접속 수를 측정해봐야 합니다.

이 체크리스트는 단순해 보이지만, 실제 서버 개발의 대부분은 이런 기본 확인을 정확히 하는 데서 출발합니다.

## 9장. 지금 당장 만들면 좋은 학습 산출물

처음부터 완성 서버를 만들려고 하면 범위가 너무 커집니다.

대신 학습 산출물을 작게 나누면 좋습니다.

첫 번째 산출물은 Mirror 샘플 실행 노트입니다.

어떤 씬에서 어떤 버튼을 누르면 어떤 상태가 되는지 기록합니다.

두 번째 산출물은 Host와 Client 로그 비교표입니다.

Host, ServerOnly, ClientOnly에서 각각 어떤 로그가 찍히는지 비교합니다.

세 번째 산출물은 서버 권위 미니 테스트입니다.

예를 들어 점수나 데미지를 서버에서만 바꿀 수 있게 만들어봅니다.

네 번째 산출물은 데디케이트 서버 빌드 스크립트 초안입니다.

Linux64 서버 빌드를 자동화하는 스크립트를 만들어봅니다.

다섯 번째 산출물은 VPS 접속 실험 기록입니다.

IP, 포트, 방화벽 설정, 접속 성공 여부, 실패 원인을 기록합니다.

여섯 번째 산출물은 운영 방향 결정 문서입니다.

매치메이킹을 직접 만들지, Edgegap이나 Multiplay 같은 호스팅을 쓸지, 혹은 다른 방식을 선택할지 정리합니다.

이 산출물들은 단순한 공부 기록이 아닙니다.

나중에 포트폴리오나 기술 문서로도 이어질 수 있습니다.

특히 게임 클라이언트 개발자 입장에서는 “서버를 직접 다뤄본 경험”을 구조적으로 설명하는 좋은 자료가 됩니다.

## 10장. 2주 학습 로드맵

이제 2주 동안 어떤 순서로 학습하면 좋을지 정리해보겠습니다.

1일차에는 용어를 정리합니다.

Server, Client, Host, Dedicated Server를 이해합니다.

Authority, Spawn, SyncVar, Command, ClientRpc 같은 Mirror 핵심 용어도 가볍게 정리합니다.

Transport, Port, Address 같은 네트워크 기본 용어도 함께 봅니다.

2일차와 3일차에는 Mirror 샘플을 실행합니다.

Host를 실행해보고, Client를 접속시켜봅니다.

Room 흐름을 확인하고, GamePlay 씬에서 동기화가 어떻게 되는지 봅니다.

4일차와 5일차에는 서버 권위 미니 기능을 만들어봅니다.

서버가 점수를 관리하게 하거나, 클라이언트 요청을 검증하고, 잘못된 요청을 무시하는 구조를 실험합니다.

6일차와 7일차에는 ServerOnly 흐름을 실험합니다.

서버 인스턴스와 클라이언트 인스턴스를 분리합니다.

로그를 기준으로 상태를 확인합니다.

포트와 주소 문제를 직접 해결해봅니다.

8일차부터 10일차까지는 데디케이트 서버 빌드를 만듭니다.

Linux 서버 빌드를 만들고, 로컬에서 실행하고, 클라이언트가 접속할 수 있는지 확인합니다.

11일차부터 14일차까지는 원격 서버 실험을 합니다.

VPS에 배포해보고, 방화벽과 포트를 설정하고, 클라이언트에서 공인 IP로 접속해봅니다.

서버 재시작 방법과 로그 확인 방법도 같이 정리합니다.

그리고 마지막으로 Docker나 쿠버네티스가 지금 당장 필요한지 판단합니다.

대부분의 경우, 처음 2주 동안은 쿠버네티스를 깊게 공부하기보다, 서버 빌드와 원격 접속을 성공시키는 것이 훨씬 중요합니다.

## 11장. 최종 판단 기준

이 문서는 최종 아키텍처 결정 문서가 아닙니다.

지금 단계에서의 정답은 명확합니다.

먼저 Mirror 샘플을 실행해서 Host, Client, ServerOnly의 차이를 몸으로 확인해야 합니다.

데디케이트 서버는 Unity 서버 빌드 타겟과 Mirror의 headless start 설정이 맞아야 제대로 동작합니다.

KCP, 포트, 방화벽은 실제 접속 실패를 해결할 때 반드시 이해해야 합니다.

쿠버네티스는 초기 학습 주제가 아닙니다. 서버 빌드와 수동 배포가 성공한 뒤에 생각할 운영 주제입니다.

그리고 PUN2보다 Mirror가 더 직접 다루는 구조라는 점을 기억해야 합니다.

Mirror를 선택한다는 것은 서버 권위 로직과 운영 책임을 프로젝트가 더 많이 가져간다는 뜻입니다.

## 에필로그

정리하겠습니다.

PUN2는 빠르게 멀티플레이를 붙이기 좋은 관리형 네트워크 솔루션에 가깝습니다.

Mirror 데디케이트 서버는 우리가 만든 Unity 서버 프로세스가 게임 상태를 직접 판단하는 구조에 가깝습니다.

이 구조는 자유도가 높고 서버 권위를 만들기 좋습니다.

하지만 서버 빌드, 포트, 방화벽, 호스팅, 로그, 재시작, 매치메이킹 같은 운영 책임도 함께 따라옵니다.

그래서 처음에는 작게 시작해야 합니다.

Host 모드로 성공합니다.

ServerOnly와 Client를 분리합니다.

로컬 서버 빌드를 실행합니다.

VPS에 올려봅니다.

그 다음 Docker나 쿠버네티스를 검토합니다.

가장 중요한 것은 처음부터 완성된 서버를 만들려고 하지 않는 것입니다.

서버가 켜진다.

클라이언트가 붙는다.

상태가 동기화된다.

이 세 가지를 먼저 성공시키는 것이 Mirror 데디케이트 서버 학습의 출발점입니다.

이상으로 Mirror 데디케이트 서버 온보딩을 마치겠습니다.
