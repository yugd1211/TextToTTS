### 본문

기준은 이천이십육년 오월 십삼일 현재 확인한 공식 자료입니다. 유니티 애셋 스토어 기준 피시넷은 무료 확장 애셋으로 등록되어 있고, 최신 표기 버전은 사 점 칠 점 이 알, 최신 릴리스 날짜는 이천이십육년 사월 이십일, 원본 유니티 버전은 이천이십일 점 삼 점 사십오입니다. 실제 프로젝트에서는 설치한 피시넷 버전에 따라 세부 이름이나 사용법이 조금 달라질 수 있으므로, 코드 작성 단계에서는 반드시 해당 버전의 공식 문서 표기를 확인해야 합니다.

일. 피시넷이란 무엇인가

피시넷은 유니티에서 멀티플레이 게임을 만들기 위한 네트워크 프레임워크입니다. 핵심 목적은 서버와 클라이언트 사이에서 게임 오브젝트, 플레이어 입력, 상태 값, 이벤트, 씬, 시간, 소유권 같은 요소를 안정적으로 주고받게 하는 것입니다.

피시넷을 이해할 때 가장 중요한 생각은 “클라이언트가 마음대로 게임 상태를 바꾸는 것이 아니라, 서버가 최종 판단을 내린다”는 것입니다. 공식 네트워크 모델 설명에서도 클라이언트 서버 구조에서 서버는 권위 있는 게임 인스턴스로서 게임 로직을 관리하고, 게임 상태를 동기화하며, 플레이어 동작을 검증하는 역할로 설명됩니다.

초보자는 피시넷을 이렇게 이해하면 됩니다.

클라이언트는 “제가 움직이고 싶습니다”, “공격 버튼을 눌렀습니다”, “아이템을 먹고 싶습니다”라고 서버에 요청합니다. 서버는 그 요청이 가능한지 검사합니다. 가능하다면 서버가 실제 게임 상태를 변경합니다. 그리고 변경된 결과를 다시 여러 클라이언트에게 알려줍니다. 이 흐름이 피시넷 네트워크 통신의 기본 골격입니다.

이. 전체 아키텍처

피시넷 프로젝트의 중심에는 네트워크 매니저가 있습니다. 네트워크 매니저는 클라이언트 매니저, 서버 매니저, 씬 매니저, 타임 매니저, 트랜스포트 매니저, 옵저버 매니저, 스태티스틱스 매니저 같은 여러 하위 매니저를 참조하고 관리합니다.

구조를 말로 그리면 다음과 같습니다.

유저 입력은 클라이언트에서 발생합니다.
클라이언트는 서버 알피시나 브로드캐스트로 서버에 요청을 보냅니다.
서버는 요청을 검증합니다.
서버는 네트워크 오브젝트의 상태를 변경합니다.
변경된 값은 싱크 바, 싱크 리스트, 옵저버스 알피시, 타깃 알피시 등으로 클라이언트에 전달됩니다.
클라이언트는 받은 정보를 화면, 애니메이션, 이펙트, 사용자 인터페이스에 반영합니다.

여기서 중요한 점은 “통신 방식”과 “상태 동기화 방식”을 구분하는 것입니다. 알피시는 사건을 전달할 때 좋습니다. 싱크 바와 싱크 타입은 상태를 유지하고 자동으로 맞출 때 좋습니다. 브로드캐스트는 특정 네트워크 오브젝트에 묶이지 않은 메시지를 보낼 때 좋습니다.

삼. 핵심 구성 요소
네트워크 매니저

네트워크 매니저는 피시넷의 중앙 관리자입니다. 서버 시작, 클라이언트 접속, 씬 동기화, 프리팹 스폰, 시간 동기화, 관찰자 관리, 트랜스포트 연결 같은 큰 흐름을 관리합니다. 초보자는 네트워크 매니저를 “멀티플레이 시스템의 본부”라고 생각하면 됩니다.

트랜스포트 매니저

트랜스포트 매니저는 실제 데이터를 네트워크를 통해 보내고 받는 밑단입니다. 피시넷의 고수준 기능은 알피시, 싱크 바, 스폰처럼 보이지만, 그 아래에서는 트랜스포트가 실제 패킷 이동을 담당합니다.

서버 매니저와 클라이언트 매니저

서버 매니저는 서버의 시작, 중지, 클라이언트 관리, 서버에서 클라이언트로 보내는 메시지 처리를 담당합니다. 클라이언트 매니저는 클라이언트 접속, 상태 관리, 클라이언트 쪽 데이터 흐름을 담당합니다.

타임 매니저

타임 매니저는 네트워크 시간과 틱 기반 처리를 담당합니다. 네트워크 게임에서는 프레임마다 처리하는 것보다 일정한 틱 단위로 입력과 상태를 처리하는 경우가 많습니다. 특히 프레딕션, 물리 동기화, 보정 시스템에서 타임 매니저가 중요합니다.

옵저버 매니저

옵저버 매니저는 어떤 클라이언트가 어떤 네트워크 오브젝트를 볼 수 있는지를 관리합니다. 예를 들어, 멀리 떨어진 적이나 다른 방에 있는 오브젝트를 모든 클라이언트에게 계속 보낼 필요는 없습니다. 옵저버 시스템을 사용하면 필요한 대상에게만 데이터를 보내 성능을 아낄 수 있습니다.

네트워크 오브젝트

네트워크 오브젝트는 네트워크로 존재를 동기화하거나 제어해야 하는 게임 오브젝트에 붙는 핵심 컴포넌트입니다. 피시넷 공식 문서의 네트워크 오브젝트 설명에서도 네트워크 초기화 여부, 스폰 가능 여부, 스폰 여부, 고유 오브젝트 식별자, 오너 정보 같은 속성을 제공합니다.

네트워크 비헤이비어

네트워크 비헤이비어는 일반 유니티 스크립트인 모노 비헤이비어처럼 동작하면서, 네트워크 상태와 네트워크 기능을 사용할 수 있게 해주는 스크립트 기반 클래스입니다. 공식 애피아이 문서에서는 네트워크 비헤이비어를 상속한 스크립트가 네트워크에 대한 정보를 얻고 네트워크 동작을 수행할 수 있다고 설명합니다.

사. 알피시 정리

알피시는 “상대편에서 함수를 실행시키는 통신 방식”입니다. 피시넷의 알피시는 크게 세 가지로 이해하면 됩니다. 공식 애피아이 문서 기준 서버 알피시는 서버로 메시지를 보내고, 옵저버스 알피시는 모든 옵저버에게 메시지를 보내며, 타깃 알피시는 특정 클라이언트 한 명에게 메시지를 보냅니다.

서버 알피시

서버 알피시는 클라이언트에서 서버로 요청을 보낼 때 사용합니다.

예를 들면 다음과 같은 상황입니다.

플레이어가 공격 버튼을 누릅니다.
클라이언트는 서버에게 “공격 요청”을 보냅니다.
서버는 공격 가능 거리, 쿨타임, 체력, 권한을 검사합니다.
검증에 성공하면 서버가 실제 공격 판정을 처리합니다.

서버 알피시는 보안상 매우 중요합니다. 클라이언트는 조작될 수 있다고 가정해야 하므로, 서버 알피시로 들어온 값은 그대로 믿지 말고 서버에서 다시 검증해야 합니다. 서버 알피시에는 소유한 클라이언트만 호출할 수 있게 제한하는 소유권 요구 옵션도 있습니다.

옵저버스 알피시

옵저버스 알피시는 특정 네트워크 오브젝트를 관찰 중인 클라이언트들에게 이벤트를 보낼 때 사용합니다.

예를 들면 다음과 같습니다.

총구 화염 이펙트 재생.
피격 사운드 재생.
폭발 이펙트 표시.
캐릭터 감정 표현 재생.

이런 정보는 “상태를 오래 저장”하기보다 “그 순간 한 번 실행”하는 이벤트에 가깝습니다. 그래서 싱크 바보다는 옵저버스 알피시가 더 자연스럽습니다.

타깃 알피시

타깃 알피시는 특정 클라이언트 한 명에게만 메시지를 보내고 싶을 때 사용합니다.

예를 들면 다음과 같습니다.

한 플레이어에게만 퀘스트 완료 창을 띄우기.
접속한 사용자에게만 개인 안내 메시지 보내기.
피격당한 플레이어에게만 화면 흔들림 적용하기.
특정 사용자에게만 인벤토리 결과 보내기.

알피시 옵션 감각

피시넷의 알피시 공통 속성에는 데이터 길이 추정, 전송 순서, 로컬 실행 같은 설정이 있습니다. 예를 들어 로컬 실행 옵션은 알피시 로직을 보내는 쪽에서도 함께 실행할 수 있게 해주는 기능입니다.

초보자 기준으로는 이렇게 기억하면 충분합니다.

클라이언트에서 서버로 요청하면 서버 알피시.
서버에서 여러 관찰자에게 이벤트를 뿌리면 옵저버스 알피시.
서버에서 특정 한 명에게만 보내면 타깃 알피시.

오. 싱크 바와 싱크 타입 정리

싱크 바는 서버에서 바뀐 단일 값을 클라이언트에 자동으로 맞춰주는 방식입니다. 공식 문서에서도 싱크 바는 단일 필드를 네트워크로 자동 동기화하는 가장 단순한 방식으로 설명됩니다.

예를 들어 체력, 닉네임, 팀 번호, 준비 상태, 현재 무기 번호 같은 값은 싱크 바에 잘 어울립니다.

싱크 타입은 싱크 바보다 넓은 개념입니다. 피시넷에는 싱크 바뿐 아니라 싱크 리스트, 싱크 딕셔너리, 싱크 해시 셋, 싱크 타이머, 싱크 스톱워치, 커스텀 싱크 타입 등이 있습니다. 공식 애피아이 문서도 싱크 오브젝트와 싱크 바가 서버에서 클라이언트로 자동 동기화되며, 값 변경은 서버에서 이뤄져야 한다고 설명합니다.

싱크 바

단일 값 동기화에 사용합니다.

좋은 예시는 체력, 점수, 이름, 준비 여부, 현재 상태입니다.

싱크 리스트

목록 동기화에 사용합니다.

좋은 예시는 접속자 목록, 인벤토리 슬롯 목록, 방 참가자 목록입니다.

싱크 딕셔너리

키와 값 형태의 데이터 동기화에 사용합니다.

좋은 예시는 플레이어 식별자별 점수, 아이템 식별자별 개수, 팀별 상태입니다.

싱크 해시 셋

중복 없는 집합 동기화에 사용합니다.

좋은 예시는 점령된 지역 목록, 이미 획득한 업적 목록, 활성화된 플래그 목록입니다.

싱크 타이머와 싱크 스톱워치

서버와 클라이언트 사이에서 타이머나 경과 시간을 효율적으로 맞출 때 사용합니다. 싱크 스톱워치는 시작과 정지 같은 상태 변화만 동기화하고 매 순간의 변화량을 계속 보내지 않는 방식으로 설명되어 있어, 시간형 데이터를 효율적으로 다룰 수 있습니다.

육. 브로드캐스트 정리

브로드캐스트는 특정 네트워크 오브젝트에 묶이지 않은 메시지를 보내고 싶을 때 사용합니다. 공식 문서에서는 브로드캐스트가 네트워크 오브젝트 컴포넌트가 없는 하나 이상의 객체에도 메시지를 보낼 수 있으며, 채팅 시스템처럼 반드시 네트워크 오브젝트가 아니어도 되는 통신에 유용하다고 설명합니다. 또한 브로드캐스트는 클라이언트에서 서버로, 서버에서 클라이언트로 보낼 수 있고, 서버 매니저나 클라이언트 매니저를 통해 사용합니다.

브로드캐스트가 어울리는 예시는 다음과 같습니다.

채팅 메시지.
로그인 요청.
인증 정보.
매치메이킹 메시지.
특정 오브젝트에 묶이지 않은 전역 알림.

알피시는 네트워크 오브젝트에 붙은 네트워크 비헤이비어의 메서드를 호출하는 감각입니다. 반면 브로드캐스트는 “구조화된 메시지”를 매니저를 통해 보내는 감각입니다.

칠. 스폰, 디스폰, 오너십

네트워크 게임에서는 오브젝트를 그냥 생성했다고 모든 클라이언트에 보이는 것이 아닙니다. 네트워크 오브젝트로 만들고, 서버가 스폰해야 다른 클라이언트에게도 네트워크 존재로 알려집니다. 피시넷 애피아이 문서에서도 스폰은 네트워크를 통해 오브젝트를 생성하며 서버에서만 호출할 수 있다고 설명합니다.

오너십은 “어떤 클라이언트가 이 오브젝트를 소유하고 있는가”를 뜻합니다. 예를 들어 플레이어 캐릭터는 보통 해당 플레이어의 클라이언트가 오너입니다. 하지만 오너라고 해서 모든 것을 마음대로 바꿀 수 있다는 뜻은 아닙니다. 보통은 오너 클라이언트가 입력을 보내고, 서버가 검증한 뒤 상태를 확정합니다.

초보자가 자주 헷갈리는 부분은 다음입니다.

게임 오브젝트 생성과 네트워크 스폰은 다릅니다.
클라이언트에서 만든 오브젝트는 서버가 인정하지 않으면 네트워크 전체에 존재하지 않습니다.
네트워크 오브젝트는 서버가 스폰해야 합니다.
오너십은 입력 권한과 관련이 있지만, 최종 권위는 서버에 두는 것이 안전합니다.

팔. 어떤 기능을 언제 써야 하는가

체력, 이름, 점수처럼 계속 유지되는 값은 싱크 바를 씁니다.

인벤토리나 참가자 목록처럼 여러 항목이 바뀌는 구조는 싱크 리스트나 싱크 딕셔너리를 씁니다.

버튼 클릭, 공격 요청, 아이템 사용 요청처럼 클라이언트가 서버에 명령을 보내는 경우는 서버 알피시를 씁니다.

폭발, 사운드, 이펙트처럼 여러 사람에게 같은 순간 이벤트를 보여주는 경우는 옵저버스 알피시를 씁니다.

한 명에게만 결과를 알려야 하는 경우는 타깃 알피시를 씁니다.

채팅, 인증, 로비 메시지처럼 특정 네트워크 오브젝트에 묶이지 않는 메시지는 브로드캐스트를 씁니다.

멀리 있는 오브젝트를 굳이 동기화하지 않으려면 옵저버 시스템을 씁니다.

움직임을 부드럽게 하고 입력 반응성을 높이고 싶다면 프레딕션과 보정을 검토합니다.

총알, 투사체, 몬스터처럼 자주 생성되고 사라지는 오브젝트가 많다면 오브젝트 풀링을 검토합니다.

구. 초보자용 구현 순서

처음에는 복잡한 프레딕션이나 보정부터 시작하지 않는 것이 좋습니다. 다음 순서가 안정적입니다.

첫째, 네트워크 매니저를 씬에 배치합니다.

둘째, 서버와 클라이언트를 시작하고 접속되는지 확인합니다.

셋째, 플레이어 프리팹에 네트워크 오브젝트를 붙입니다.

넷째, 플레이어 스폰이 서버 기준으로 되는지 확인합니다.

다섯째, 플레이어 스크립트를 네트워크 비헤이비어로 만듭니다.

여섯째, 입력은 클라이언트에서 받고, 실제 상태 변경은 서버에서 처리합니다.

일곱째, 체력이나 점수 같은 값은 싱크 바로 동기화합니다.

여덟째, 공격 이펙트나 사운드는 옵저버스 알피시로 보냅니다.

아홉째, 개인 알림은 타깃 알피시로 보냅니다.

열째, 채팅이나 인증 같은 전역 메시지는 브로드캐스트로 분리합니다.

십. 초보자가 기억해야 할 핵심 원칙

가장 중요한 원칙은 서버 권위입니다. 클라이언트는 요청하고, 서버는 판단합니다.

두 번째 원칙은 상태와 이벤트를 구분하는 것입니다. 상태는 싱크 바와 싱크 타입으로 맞추고, 이벤트는 알피시로 보냅니다.

세 번째 원칙은 필요한 사람에게만 보내는 것입니다. 모든 데이터를 모든 클라이언트에게 보내면 성능이 나빠집니다. 옵저버 시스템과 관심 영역을 활용해야 합니다.

네 번째 원칙은 서버에서 스폰하는 것입니다. 네트워크 오브젝트는 서버가 스폰해야 네트워크 전체에 알려집니다.

다섯 번째 원칙은 코드 작성 전에 용어를 명확히 하는 것입니다. 네트워크 매니저, 네트워크 오브젝트, 네트워크 비헤이비어, 알피시, 싱크 타입, 오너십, 옵저버를 이해하면 피시넷의 대부분 기능을 읽을 수 있습니다.

오디오북 나레이션용 스크립트

아래는 바로 읽는 용도로 만든 대본입니다. 코드용 정식 표기는 넣지 않고, 기술 용어는 한글 발음 표기로 통일했습니다.

도입

이번 설명에서는 유니티에서 멀티플레이 게임을 만들 때 사용하는 피시넷의 기본 개념을 알아보겠습니다.

피시넷을 처음 보면 용어가 많아서 어렵게 느껴질 수 있습니다. 네트워크 매니저, 네트워크 오브젝트, 네트워크 비헤이비어, 알피시, 싱크 바, 싱크 타입, 오너십, 옵저버 시스템 같은 말이 계속 나오기 때문입니다.

하지만 전체 구조를 먼저 잡으면 어렵지 않습니다.

피시넷의 핵심은 간단합니다.

클라이언트는 요청합니다.
서버는 판단합니다.
서버가 상태를 바꿉니다.
클라이언트들은 서버가 바꾼 결과를 받아 화면에 보여줍니다.

이 네 문장이 피시넷 네트워크 구조의 중심입니다.

챕터 일. 피시넷의 기본 생각

피시넷은 유니티 게임을 멀티플레이로 만들기 위한 네트워크 프레임워크입니다.

혼자 하는 게임에서는 한 컴퓨터 안에서 모든 일이 끝납니다. 플레이어가 움직이면 바로 위치가 바뀌고, 공격 버튼을 누르면 바로 공격이 실행됩니다.

하지만 멀티플레이 게임에서는 여러 명의 컴퓨터가 같은 게임 상태를 공유해야 합니다. 한 명의 화면에서 적이 죽었는데, 다른 사람 화면에서는 살아 있으면 안 됩니다. 한 명은 문이 열렸다고 보는데, 다른 사람은 문이 닫혀 있다고 보면 안 됩니다.

그래서 멀티플레이 게임에는 기준이 필요합니다. 그 기준 역할을 하는 것이 서버입니다.

클라이언트는 플레이어가 조작하는 쪽입니다. 서버는 게임의 최종 판단을 내리는 쪽입니다.

예를 들어 플레이어가 공격 버튼을 눌렀다고 해보겠습니다. 클라이언트는 서버에게 “공격하고 싶습니다”라고 요청합니다. 서버는 공격 거리가 맞는지, 공격 쿨타임이 끝났는지, 플레이어가 살아 있는지 확인합니다. 조건이 맞으면 서버가 공격을 인정합니다. 그리고 그 결과를 다른 클라이언트에게 알려줍니다.

이렇게 해야 치트나 잘못된 상태를 줄일 수 있습니다. 그래서 피시넷을 사용할 때는 항상 “서버가 최종 판단을 한다”는 생각을 기본으로 가져가야 합니다.

챕터 이. 전체 흐름

피시넷의 전체 흐름은 이렇게 이해할 수 있습니다.

첫째, 유저가 키보드나 마우스로 입력합니다.

둘째, 클라이언트는 그 입력을 서버에 보냅니다.

셋째, 서버는 입력이 올바른지 검사합니다.

넷째, 서버는 게임 상태를 바꿉니다.

다섯째, 바뀐 상태나 이벤트를 클라이언트들에게 보냅니다.

여섯째, 클라이언트는 받은 정보를 화면에 보여줍니다.

여기서 상태와 이벤트를 구분해야 합니다.

상태는 계속 유지되는 값입니다. 체력, 점수, 닉네임, 현재 무기, 준비 완료 여부가 상태입니다.

이벤트는 순간적으로 일어나는 일입니다. 총소리, 폭발, 피격 이펙트, 버튼 클릭 결과, 알림 창 표시가 이벤트입니다.

상태는 주로 싱크 바와 싱크 타입으로 동기화합니다. 이벤트는 주로 알피시로 전달합니다.

이 구분을 잘하면 네트워크 코드를 훨씬 깔끔하게 설계할 수 있습니다.

챕터 삼. 네트워크 매니저

피시넷의 중심에는 네트워크 매니저가 있습니다.

네트워크 매니저는 멀티플레이 시스템의 본부입니다. 서버를 시작하고, 클라이언트를 연결하고, 씬을 관리하고, 네트워크 오브젝트를 스폰하고, 시간을 맞추고, 통신 흐름을 관리합니다.

네트워크 매니저 아래에는 여러 매니저가 있습니다.

서버 매니저는 서버 쪽 일을 담당합니다.
클라이언트 매니저는 클라이언트 쪽 일을 담당합니다.
트랜스포트 매니저는 실제 네트워크 데이터 이동을 담당합니다.
타임 매니저는 네트워크 시간과 틱을 담당합니다.
씬 매니저는 멀티플레이 씬 로딩을 담당합니다.
옵저버 매니저는 어떤 클라이언트가 어떤 오브젝트를 볼 수 있는지 담당합니다.
스태티스틱스 매니저는 네트워크 트래픽 같은 통계 정보를 확인할 때 사용합니다.

초보자는 처음에 모든 매니저를 깊게 외울 필요는 없습니다. 먼저 네트워크 매니저가 전체를 관리하고, 나머지 매니저들이 각 분야를 나눠 맡는다고 이해하면 충분합니다.

챕터 사. 네트워크 오브젝트와 네트워크 비헤이비어

피시넷에서 네트워크로 동기화할 오브젝트에는 네트워크 오브젝트가 필요합니다.

그냥 유니티 게임 오브젝트를 만들었다고 해서 자동으로 모든 클라이언트에게 보이는 것은 아닙니다. 네트워크로 존재해야 하는 오브젝트라면 네트워크 오브젝트로 만들어야 합니다.

예를 들어 플레이어 캐릭터, 몬스터, 투사체, 네트워크로 공유되는 문, 점령 지점 같은 것들이 네트워크 오브젝트가 될 수 있습니다.

그다음 중요한 것이 네트워크 비헤이비어입니다.

일반 유니티 스크립트는 모노 비헤이비어를 상속합니다. 피시넷에서 네트워크 기능을 쓰는 스크립트는 네트워크 비헤이비어를 상속합니다.

네트워크 비헤이비어를 사용하면 서버인지, 클라이언트인지, 오너인지, 스폰된 상태인지 같은 네트워크 정보를 확인할 수 있습니다. 또한 서버 알피시, 옵저버스 알피시, 타깃 알피시 같은 통신 기능을 사용할 수 있습니다.

간단히 말하면 네트워크 오브젝트는 네트워크에 존재하는 몸체이고, 네트워크 비헤이비어는 그 몸체 안에서 네트워크 로직을 실행하는 스크립트입니다.

챕터 오. 알피시

알피시는 원격으로 함수를 실행시키는 방식입니다.

피시넷에서는 알피시를 크게 세 가지로 나눠 생각하면 됩니다.

첫째, 서버 알피시.
둘째, 옵저버스 알피시.
셋째, 타깃 알피시.

서버 알피시는 클라이언트에서 서버로 보내는 요청입니다.

플레이어가 공격 버튼을 눌렀습니다. 클라이언트는 서버에게 공격 요청을 보냅니다. 이때 서버 알피시를 사용합니다.

플레이어가 아이템을 먹으려 합니다. 클라이언트는 서버에게 아이템 획득 요청을 보냅니다. 이때도 서버 알피시를 사용합니다.

서버 알피시는 반드시 검증이 필요합니다. 클라이언트가 보낸 값은 믿으면 안 됩니다. 서버는 거리, 상태, 권한, 쿨타임, 체력 같은 조건을 다시 확인해야 합니다.

옵저버스 알피시는 서버에서 여러 관찰자에게 이벤트를 보내는 방식입니다.

예를 들어 폭발 이펙트를 보여주거나, 총소리를 재생하거나, 캐릭터의 피격 애니메이션을 실행할 때 사용할 수 있습니다.

여기서 옵저버란 해당 네트워크 오브젝트를 볼 수 있는 클라이언트를 뜻합니다. 모든 클라이언트가 아니라, 필요한 클라이언트에게만 보내는 것이 중요합니다.

타깃 알피시는 서버에서 특정 클라이언트 한 명에게만 메시지를 보낼 때 사용합니다.

예를 들어 한 플레이어에게만 퀘스트 완료 창을 띄우거나, 한 플레이어에게만 개인 보상 결과를 보여주거나, 특정 클라이언트에게만 화면 흔들림을 적용할 수 있습니다.

정리하면 이렇습니다.

클라이언트에서 서버로 보내면 서버 알피시.
서버에서 여러 관찰자에게 보내면 옵저버스 알피시.
서버에서 한 명에게만 보내면 타깃 알피시.

챕터 육. 싱크 바와 싱크 타입

싱크 바는 서버에서 바뀐 값을 클라이언트에게 자동으로 맞춰주는 기능입니다.

가장 쉬운 예는 체력입니다.

서버에서 플레이어 체력이 백에서 칠십으로 바뀌면, 클라이언트도 그 값을 칠십으로 받습니다. 그래서 화면의 체력 바가 올바르게 표시됩니다.

싱크 바는 단일 값에 잘 맞습니다. 체력, 점수, 닉네임, 팀 번호, 준비 상태, 현재 무기 같은 값이 좋은 예입니다.

하지만 게임에는 단일 값만 있는 것이 아닙니다. 목록이나 사전 형태의 데이터도 있습니다. 이럴 때는 싱크 타입을 사용합니다.

싱크 리스트는 목록을 동기화합니다. 접속자 목록, 인벤토리 목록, 방 참가자 목록에 어울립니다.

싱크 딕셔너리는 키와 값 구조를 동기화합니다. 플레이어별 점수, 아이템별 개수, 팀별 점수에 어울립니다.

싱크 해시 셋은 중복 없는 집합을 동기화합니다. 점령된 지역 목록, 이미 획득한 업적 목록, 활성화된 상태 목록에 어울립니다.

싱크 타이머와 싱크 스톱워치는 시간 관련 값을 동기화할 때 사용합니다. 제한 시간, 쿨타임, 경기 시간처럼 서버와 클라이언트가 같은 시간 감각을 가져야 할 때 도움이 됩니다.

싱크 타입을 사용할 때 가장 중요한 원칙은 서버에서 값을 바꾸는 것입니다. 클라이언트가 직접 값을 바꾸는 구조로 만들면 상태가 꼬일 수 있습니다.

챕터 칠. 브로드캐스트

브로드캐스트는 특정 네트워크 오브젝트에 묶이지 않은 메시지를 보낼 때 사용합니다.

알피시는 보통 네트워크 오브젝트와 네트워크 비헤이비어에 연결된 함수 호출입니다. 반면 브로드캐스트는 구조화된 메시지를 보내는 방식입니다.

예를 들어 채팅 메시지를 생각해보겠습니다. 채팅은 반드시 특정 캐릭터 오브젝트의 함수에 묶일 필요가 없습니다. 클라이언트가 채팅 메시지를 서버에 보내고, 서버가 다시 필요한 클라이언트에게 전달하면 됩니다.

이럴 때 브로드캐스트가 잘 맞습니다.

브로드캐스트는 채팅, 인증, 로비 메시지, 매치메이킹, 전역 알림처럼 특정 오브젝트에 종속되지 않은 통신에 유용합니다.

초보자는 이렇게 구분하면 됩니다.

네트워크 오브젝트의 동작을 호출하고 싶으면 알피시.
오브젝트와 상관없는 메시지를 보내고 싶으면 브로드캐스트.

챕터 팔. 스폰과 디스폰

멀티플레이에서 오브젝트를 생성할 때는 스폰 개념이 중요합니다.

유니티에서 그냥 오브젝트를 생성하는 것과 피시넷에서 네트워크 오브젝트를 스폰하는 것은 다릅니다.

그냥 생성하면 내 컴퓨터에만 생길 수 있습니다.
네트워크 스폰을 하면 서버가 그 오브젝트의 존재를 네트워크 전체에 알려줍니다.

피시넷에서는 네트워크 오브젝트 스폰을 서버 기준으로 처리해야 합니다.

예를 들어 몬스터를 생성한다고 해보겠습니다. 클라이언트가 마음대로 몬스터를 생성하면 다른 클라이언트와 상태가 맞지 않을 수 있습니다. 서버가 몬스터를 스폰하고, 그 결과를 클라이언트들에게 알려야 합니다.

디스폰은 반대로 네트워크 오브젝트를 네트워크에서 제거하는 것입니다. 몬스터가 죽었거나, 투사체가 사라졌거나, 아이템을 획득해서 없어져야 할 때 디스폰합니다.

스폰과 디스폰은 네트워크 오브젝트의 생명 주기를 관리하는 핵심입니다.

챕터 구. 오너십

오너십은 어떤 클라이언트가 어떤 네트워크 오브젝트를 소유하고 있는지를 나타냅니다.

예를 들어 내 플레이어 캐릭터는 보통 내 클라이언트가 오너입니다. 그래서 내 클라이언트는 그 캐릭터에 대한 입력을 보낼 수 있습니다.

하지만 오너라고 해서 모든 것을 마음대로 바꿀 수 있다는 뜻은 아닙니다.

안전한 구조에서는 오너 클라이언트가 입력을 보내고, 서버가 그 입력을 검증합니다. 검증 후 서버가 실제 위치, 체력, 공격 결과 같은 상태를 확정합니다.

오너십은 입력 권한과 관련이 있습니다. 하지만 게임 상태의 최종 결정권은 서버에 두는 것이 좋습니다.

이 원칙을 지키면 치트, 동기화 오류, 상태 불일치를 줄일 수 있습니다.

챕터 십. 옵저버 시스템

옵저버 시스템은 누가 어떤 오브젝트를 볼 수 있는지 정하는 시스템입니다.

멀티플레이 게임에서 모든 오브젝트의 모든 정보를 모든 클라이언트에게 보내면 성능이 나빠집니다.

예를 들어 넓은 월드가 있다고 해보겠습니다. 서울에 있는 플레이어에게 부산에 있는 몬스터의 세부 상태를 계속 보낼 필요는 없습니다. 같은 방에 있지 않은 플레이어에게 다른 방의 세부 정보를 계속 보낼 필요도 없습니다.

옵저버 시스템은 이런 낭비를 줄입니다.

가까운 사람에게만 보냅니다.
같은 씬에 있는 사람에게만 보냅니다.
같은 매치에 있는 사람에게만 보냅니다.
오너에게만 보냅니다.

이런 식으로 필요한 클라이언트에게만 데이터를 보내면 네트워크 트래픽을 줄일 수 있습니다.

초보자는 옵저버 시스템을 “보낼 사람을 고르는 필터”라고 이해하면 됩니다.

챕터 십일. 프레딕션과 보정

네트워크 게임에서는 지연 시간이 있습니다.

플레이어가 이동 키를 눌렀는데 서버 응답을 기다린 뒤 움직이면 조작감이 답답해집니다. 그래서 클라이언트는 먼저 움직였다고 예측할 수 있습니다. 이것을 프레딕션이라고 부릅니다.

프레딕션은 클라이언트가 자기 입력 결과를 미리 보여주는 기술입니다.

하지만 서버의 최종 결과와 클라이언트의 예측이 다를 수 있습니다. 이때 서버 결과에 맞게 다시 조정해야 합니다. 이것이 보정입니다.

프레딕션과 보정은 고급 기능입니다. 처음부터 바로 적용하려고 하면 어렵습니다.

처음에는 서버 알피시, 싱크 바, 옵저버스 알피시로 기본 구조를 만들고, 움직임이 어색하거나 반응성이 부족할 때 프레딕션을 공부하는 것이 좋습니다.

챕터 십이. 처음 만들 때의 추천 순서

처음 피시넷을 배울 때는 작은 예제부터 만드는 것이 좋습니다.

첫 번째 목표는 서버와 클라이언트를 연결하는 것입니다.

두 번째 목표는 플레이어를 스폰하는 것입니다.

세 번째 목표는 플레이어의 체력을 싱크 바로 동기화하는 것입니다.

네 번째 목표는 공격 버튼을 누르면 서버 알피시로 서버에 요청하는 것입니다.

다섯 번째 목표는 서버가 공격을 검증하고 체력을 줄이는 것입니다.

여섯 번째 목표는 피격 이펙트를 옵저버스 알피시로 보여주는 것입니다.

일곱 번째 목표는 한 명에게만 메시지를 보내는 타깃 알피시를 써보는 것입니다.

여덟 번째 목표는 채팅 메시지를 브로드캐스트로 만들어보는 것입니다.

이 순서대로 하면 피시넷의 핵심 통신 방식을 자연스럽게 익힐 수 있습니다.

마무리

피시넷을 처음 배울 때 가장 중요한 것은 용어를 많이 외우는 것이 아닙니다. 흐름을 이해하는 것입니다.

클라이언트는 요청합니다.
서버는 검증합니다.
서버는 상태를 바꿉니다.
클라이언트는 결과를 받습니다.

상태는 싱크 바와 싱크 타입으로 맞춥니다.
이벤트는 알피시로 보냅니다.
오브젝트와 관계없는 메시지는 브로드캐스트로 보냅니다.
네트워크 오브젝트는 서버가 스폰합니다.
오너십은 입력 권한과 관련되지만, 최종 권위는 서버에 둡니다.
옵저버 시스템은 필요한 사람에게만 데이터를 보내기 위한 필터입니다.

이 기본 구조를 이해하면, 피시넷 문서를 읽을 때 훨씬 덜 어렵게 느껴집니다.

처음에는 작은 멀티플레이 예제 하나를 완성하는 것을 목표로 하세요.
서버 접속, 플레이어 스폰, 체력 동기화, 공격 요청, 이펙트 전달까지 만들 수 있다면 피시넷의 핵심은 이미 잡은 것입니다.

일. 피시넷이란 무엇인가

피시넷은 유니티에서 멀티플레이 게임을 만들기 위한 네트워크 프레임워크입니다. 핵심 목적은 서버와 클라이언트 사이에서 게임 오브젝트, 플레이어 입력, 상태 값, 이벤트, 씬, 시간, 소유권 같은 요소를 안정적으로 주고받게 하는 것입니다.

피시넷을 이해할 때 가장 중요한 생각은 “클라이언트가 마음대로 게임 상태를 바꾸는 것이 아니라, 서버가 최종 판단을 내린다”는 것입니다. 공식 네트워크 모델 설명에서도 클라이언트 서버 구조에서 서버는 권위 있는 게임 인스턴스로서 게임 로직을 관리하고, 게임 상태를 동기화하며, 플레이어 동작을 검증하는 역할로 설명됩니다.

초보자는 피시넷을 이렇게 이해하면 됩니다.

클라이언트는 “제가 움직이고 싶습니다”, “공격 버튼을 눌렀습니다”, “아이템을 먹고 싶습니다”라고 서버에 요청합니다. 서버는 그 요청이 가능한지 검사합니다. 가능하다면 서버가 실제 게임 상태를 변경합니다. 그리고 변경된 결과를 다시 여러 클라이언트에게 알려줍니다. 이 흐름이 피시넷 네트워크 통신의 기본 골격입니다.

이. 전체 아키텍처

피시넷 프로젝트의 중심에는 네트워크 매니저가 있습니다. 네트워크 매니저는 클라이언트 매니저, 서버 매니저, 씬 매니저, 타임 매니저, 트랜스포트 매니저, 옵저버 매니저, 스태티스틱스 매니저 같은 여러 하위 매니저를 참조하고 관리합니다.

구조를 말로 그리면 다음과 같습니다.

유저 입력은 클라이언트에서 발생합니다.
클라이언트는 서버 알피시나 브로드캐스트로 서버에 요청을 보냅니다.
서버는 요청을 검증합니다.
서버는 네트워크 오브젝트의 상태를 변경합니다.
변경된 값은 싱크 바, 싱크 리스트, 옵저버스 알피시, 타깃 알피시 등으로 클라이언트에 전달됩니다.
클라이언트는 받은 정보를 화면, 애니메이션, 이펙트, 사용자 인터페이스에 반영합니다.

여기서 중요한 점은 “통신 방식”과 “상태 동기화 방식”을 구분하는 것입니다. 알피시는 사건을 전달할 때 좋습니다. 싱크 바와 싱크 타입은 상태를 유지하고 자동으로 맞출 때 좋습니다. 브로드캐스트는 특정 네트워크 오브젝트에 묶이지 않은 메시지를 보낼 때 좋습니다.

삼. 핵심 구성 요소
네트워크 매니저

네트워크 매니저는 피시넷의 중앙 관리자입니다. 서버 시작, 클라이언트 접속, 씬 동기화, 프리팹 스폰, 시간 동기화, 관찰자 관리, 트랜스포트 연결 같은 큰 흐름을 관리합니다. 초보자는 네트워크 매니저를 “멀티플레이 시스템의 본부”라고 생각하면 됩니다.

트랜스포트 매니저

트랜스포트 매니저는 실제 데이터를 네트워크를 통해 보내고 받는 밑단입니다. 피시넷의 고수준 기능은 알피시, 싱크 바, 스폰처럼 보이지만, 그 아래에서는 트랜스포트가 실제 패킷 이동을 담당합니다.

서버 매니저와 클라이언트 매니저

서버 매니저는 서버의 시작, 중지, 클라이언트 관리, 서버에서 클라이언트로 보내는 메시지 처리를 담당합니다. 클라이언트 매니저는 클라이언트 접속, 상태 관리, 클라이언트 쪽 데이터 흐름을 담당합니다.

타임 매니저

타임 매니저는 네트워크 시간과 틱 기반 처리를 담당합니다. 네트워크 게임에서는 프레임마다 처리하는 것보다 일정한 틱 단위로 입력과 상태를 처리하는 경우가 많습니다. 특히 프레딕션, 물리 동기화, 보정 시스템에서 타임 매니저가 중요합니다.

옵저버 매니저

옵저버 매니저는 어떤 클라이언트가 어떤 네트워크 오브젝트를 볼 수 있는지를 관리합니다. 예를 들어, 멀리 떨어진 적이나 다른 방에 있는 오브젝트를 모든 클라이언트에게 계속 보낼 필요는 없습니다. 옵저버 시스템을 사용하면 필요한 대상에게만 데이터를 보내 성능을 아낄 수 있습니다.

네트워크 오브젝트

네트워크 오브젝트는 네트워크로 존재를 동기화하거나 제어해야 하는 게임 오브젝트에 붙는 핵심 컴포넌트입니다. 피시넷 공식 문서의 네트워크 오브젝트 설명에서도 네트워크 초기화 여부, 스폰 가능 여부, 스폰 여부, 고유 오브젝트 식별자, 오너 정보 같은 속성을 제공합니다.

네트워크 비헤이비어

네트워크 비헤이비어는 일반 유니티 스크립트인 모노 비헤이비어처럼 동작하면서, 네트워크 상태와 네트워크 기능을 사용할 수 있게 해주는 스크립트 기반 클래스입니다. 공식 애피아이 문서에서는 네트워크 비헤이비어를 상속한 스크립트가 네트워크에 대한 정보를 얻고 네트워크 동작을 수행할 수 있다고 설명합니다.

사. 알피시 정리

알피시는 “상대편에서 함수를 실행시키는 통신 방식”입니다. 피시넷의 알피시는 크게 세 가지로 이해하면 됩니다. 공식 애피아이 문서 기준 서버 알피시는 서버로 메시지를 보내고, 옵저버스 알피시는 모든 옵저버에게 메시지를 보내며, 타깃 알피시는 특정 클라이언트 한 명에게 메시지를 보냅니다.

서버 알피시

서버 알피시는 클라이언트에서 서버로 요청을 보낼 때 사용합니다.

예를 들면 다음과 같은 상황입니다.

플레이어가 공격 버튼을 누릅니다.
클라이언트는 서버에게 “공격 요청”을 보냅니다.
서버는 공격 가능 거리, 쿨타임, 체력, 권한을 검사합니다.
검증에 성공하면 서버가 실제 공격 판정을 처리합니다.

서버 알피시는 보안상 매우 중요합니다. 클라이언트는 조작될 수 있다고 가정해야 하므로, 서버 알피시로 들어온 값은 그대로 믿지 말고 서버에서 다시 검증해야 합니다. 서버 알피시에는 소유한 클라이언트만 호출할 수 있게 제한하는 소유권 요구 옵션도 있습니다.

옵저버스 알피시

옵저버스 알피시는 특정 네트워크 오브젝트를 관찰 중인 클라이언트들에게 이벤트를 보낼 때 사용합니다.

예를 들면 다음과 같습니다.

총구 화염 이펙트 재생.
피격 사운드 재생.
폭발 이펙트 표시.
캐릭터 감정 표현 재생.

이런 정보는 “상태를 오래 저장”하기보다 “그 순간 한 번 실행”하는 이벤트에 가깝습니다. 그래서 싱크 바보다는 옵저버스 알피시가 더 자연스럽습니다.

타깃 알피시

타깃 알피시는 특정 클라이언트 한 명에게만 메시지를 보내고 싶을 때 사용합니다.

예를 들면 다음과 같습니다.

한 플레이어에게만 퀘스트 완료 창을 띄우기.
접속한 사용자에게만 개인 안내 메시지 보내기.
피격당한 플레이어에게만 화면 흔들림 적용하기.
특정 사용자에게만 인벤토리 결과 보내기.

알피시 옵션 감각

피시넷의 알피시 공통 속성에는 데이터 길이 추정, 전송 순서, 로컬 실행 같은 설정이 있습니다. 예를 들어 로컬 실행 옵션은 알피시 로직을 보내는 쪽에서도 함께 실행할 수 있게 해주는 기능입니다.

초보자 기준으로는 이렇게 기억하면 충분합니다.

클라이언트에서 서버로 요청하면 서버 알피시.
서버에서 여러 관찰자에게 이벤트를 뿌리면 옵저버스 알피시.
서버에서 특정 한 명에게만 보내면 타깃 알피시.

오. 싱크 바와 싱크 타입 정리

싱크 바는 서버에서 바뀐 단일 값을 클라이언트에 자동으로 맞춰주는 방식입니다. 공식 문서에서도 싱크 바는 단일 필드를 네트워크로 자동 동기화하는 가장 단순한 방식으로 설명됩니다.

예를 들어 체력, 닉네임, 팀 번호, 준비 상태, 현재 무기 번호 같은 값은 싱크 바에 잘 어울립니다.

싱크 타입은 싱크 바보다 넓은 개념입니다. 피시넷에는 싱크 바뿐 아니라 싱크 리스트, 싱크 딕셔너리, 싱크 해시 셋, 싱크 타이머, 싱크 스톱워치, 커스텀 싱크 타입 등이 있습니다. 공식 애피아이 문서도 싱크 오브젝트와 싱크 바가 서버에서 클라이언트로 자동 동기화되며, 값 변경은 서버에서 이뤄져야 한다고 설명합니다.

싱크 바

단일 값 동기화에 사용합니다.

좋은 예시는 체력, 점수, 이름, 준비 여부, 현재 상태입니다.

싱크 리스트

목록 동기화에 사용합니다.

좋은 예시는 접속자 목록, 인벤토리 슬롯 목록, 방 참가자 목록입니다.

싱크 딕셔너리

키와 값 형태의 데이터 동기화에 사용합니다.

좋은 예시는 플레이어 식별자별 점수, 아이템 식별자별 개수, 팀별 상태입니다.

싱크 해시 셋

중복 없는 집합 동기화에 사용합니다.

좋은 예시는 점령된 지역 목록, 이미 획득한 업적 목록, 활성화된 플래그 목록입니다.

싱크 타이머와 싱크 스톱워치

서버와 클라이언트 사이에서 타이머나 경과 시간을 효율적으로 맞출 때 사용합니다. 싱크 스톱워치는 시작과 정지 같은 상태 변화만 동기화하고 매 순간의 변화량을 계속 보내지 않는 방식으로 설명되어 있어, 시간형 데이터를 효율적으로 다룰 수 있습니다.

육. 브로드캐스트 정리

브로드캐스트는 특정 네트워크 오브젝트에 묶이지 않은 메시지를 보내고 싶을 때 사용합니다. 공식 문서에서는 브로드캐스트가 네트워크 오브젝트 컴포넌트가 없는 하나 이상의 객체에도 메시지를 보낼 수 있으며, 채팅 시스템처럼 반드시 네트워크 오브젝트가 아니어도 되는 통신에 유용하다고 설명합니다. 또한 브로드캐스트는 클라이언트에서 서버로, 서버에서 클라이언트로 보낼 수 있고, 서버 매니저나 클라이언트 매니저를 통해 사용합니다.

브로드캐스트가 어울리는 예시는 다음과 같습니다.

채팅 메시지.
로그인 요청.
인증 정보.
매치메이킹 메시지.
특정 오브젝트에 묶이지 않은 전역 알림.

알피시는 네트워크 오브젝트에 붙은 네트워크 비헤이비어의 메서드를 호출하는 감각입니다. 반면 브로드캐스트는 “구조화된 메시지”를 매니저를 통해 보내는 감각입니다.

칠. 스폰, 디스폰, 오너십

네트워크 게임에서는 오브젝트를 그냥 생성했다고 모든 클라이언트에 보이는 것이 아닙니다. 네트워크 오브젝트로 만들고, 서버가 스폰해야 다른 클라이언트에게도 네트워크 존재로 알려집니다. 피시넷 애피아이 문서에서도 스폰은 네트워크를 통해 오브젝트를 생성하며 서버에서만 호출할 수 있다고 설명합니다.

오너십은 “어떤 클라이언트가 이 오브젝트를 소유하고 있는가”를 뜻합니다. 예를 들어 플레이어 캐릭터는 보통 해당 플레이어의 클라이언트가 오너입니다. 하지만 오너라고 해서 모든 것을 마음대로 바꿀 수 있다는 뜻은 아닙니다. 보통은 오너 클라이언트가 입력을 보내고, 서버가 검증한 뒤 상태를 확정합니다.

초보자가 자주 헷갈리는 부분은 다음입니다.

게임 오브젝트 생성과 네트워크 스폰은 다릅니다.
클라이언트에서 만든 오브젝트는 서버가 인정하지 않으면 네트워크 전체에 존재하지 않습니다.
네트워크 오브젝트는 서버가 스폰해야 합니다.
오너십은 입력 권한과 관련이 있지만, 최종 권위는 서버에 두는 것이 안전합니다.

팔. 어떤 기능을 언제 써야 하는가

체력, 이름, 점수처럼 계속 유지되는 값은 싱크 바를 씁니다.

인벤토리나 참가자 목록처럼 여러 항목이 바뀌는 구조는 싱크 리스트나 싱크 딕셔너리를 씁니다.

버튼 클릭, 공격 요청, 아이템 사용 요청처럼 클라이언트가 서버에 명령을 보내는 경우는 서버 알피시를 씁니다.

폭발, 사운드, 이펙트처럼 여러 사람에게 같은 순간 이벤트를 보여주는 경우는 옵저버스 알피시를 씁니다.

한 명에게만 결과를 알려야 하는 경우는 타깃 알피시를 씁니다.

채팅, 인증, 로비 메시지처럼 특정 네트워크 오브젝트에 묶이지 않는 메시지는 브로드캐스트를 씁니다.

멀리 있는 오브젝트를 굳이 동기화하지 않으려면 옵저버 시스템을 씁니다.

움직임을 부드럽게 하고 입력 반응성을 높이고 싶다면 프레딕션과 보정을 검토합니다.

총알, 투사체, 몬스터처럼 자주 생성되고 사라지는 오브젝트가 많다면 오브젝트 풀링을 검토합니다.

구. 초보자용 구현 순서

처음에는 복잡한 프레딕션이나 보정부터 시작하지 않는 것이 좋습니다. 다음 순서가 안정적입니다.

첫째, 네트워크 매니저를 씬에 배치합니다.

둘째, 서버와 클라이언트를 시작하고 접속되는지 확인합니다.

셋째, 플레이어 프리팹에 네트워크 오브젝트를 붙입니다.

넷째, 플레이어 스폰이 서버 기준으로 되는지 확인합니다.

다섯째, 플레이어 스크립트를 네트워크 비헤이비어로 만듭니다.

여섯째, 입력은 클라이언트에서 받고, 실제 상태 변경은 서버에서 처리합니다.

일곱째, 체력이나 점수 같은 값은 싱크 바로 동기화합니다.

여덟째, 공격 이펙트나 사운드는 옵저버스 알피시로 보냅니다.

아홉째, 개인 알림은 타깃 알피시로 보냅니다.

열째, 채팅이나 인증 같은 전역 메시지는 브로드캐스트로 분리합니다.

십. 초보자가 기억해야 할 핵심 원칙

가장 중요한 원칙은 서버 권위입니다. 클라이언트는 요청하고, 서버는 판단합니다.

두 번째 원칙은 상태와 이벤트를 구분하는 것입니다. 상태는 싱크 바와 싱크 타입으로 맞추고, 이벤트는 알피시로 보냅니다.

세 번째 원칙은 필요한 사람에게만 보내는 것입니다. 모든 데이터를 모든 클라이언트에게 보내면 성능이 나빠집니다. 옵저버 시스템과 관심 영역을 활용해야 합니다.

네 번째 원칙은 서버에서 스폰하는 것입니다. 네트워크 오브젝트는 서버가 스폰해야 네트워크 전체에 알려집니다.

다섯 번째 원칙은 코드 작성 전에 용어를 명확히 하는 것입니다. 네트워크 매니저, 네트워크 오브젝트, 네트워크 비헤이비어, 알피시, 싱크 타입, 오너십, 옵저버를 이해하면 피시넷의 대부분 기능을 읽을 수 있습니다.

오디오북 나레이션용 스크립트

아래는 바로 읽는 용도로 만든 대본입니다. 코드용 정식 표기는 넣지 않고, 기술 용어는 한글 발음 표기로 통일했습니다.

도입

이번 설명에서는 유니티에서 멀티플레이 게임을 만들 때 사용하는 피시넷의 기본 개념을 알아보겠습니다.

피시넷을 처음 보면 용어가 많아서 어렵게 느껴질 수 있습니다. 네트워크 매니저, 네트워크 오브젝트, 네트워크 비헤이비어, 알피시, 싱크 바, 싱크 타입, 오너십, 옵저버 시스템 같은 말이 계속 나오기 때문입니다.

하지만 전체 구조를 먼저 잡으면 어렵지 않습니다.

피시넷의 핵심은 간단합니다.

클라이언트는 요청합니다.
서버는 판단합니다.
서버가 상태를 바꿉니다.
클라이언트들은 서버가 바꾼 결과를 받아 화면에 보여줍니다.

이 네 문장이 피시넷 네트워크 구조의 중심입니다.

챕터 일. 피시넷의 기본 생각

피시넷은 유니티 게임을 멀티플레이로 만들기 위한 네트워크 프레임워크입니다.

혼자 하는 게임에서는 한 컴퓨터 안에서 모든 일이 끝납니다. 플레이어가 움직이면 바로 위치가 바뀌고, 공격 버튼을 누르면 바로 공격이 실행됩니다.

하지만 멀티플레이 게임에서는 여러 명의 컴퓨터가 같은 게임 상태를 공유해야 합니다. 한 명의 화면에서 적이 죽었는데, 다른 사람 화면에서는 살아 있으면 안 됩니다. 한 명은 문이 열렸다고 보는데, 다른 사람은 문이 닫혀 있다고 보면 안 됩니다.

그래서 멀티플레이 게임에는 기준이 필요합니다. 그 기준 역할을 하는 것이 서버입니다.

클라이언트는 플레이어가 조작하는 쪽입니다. 서버는 게임의 최종 판단을 내리는 쪽입니다.

예를 들어 플레이어가 공격 버튼을 눌렀다고 해보겠습니다. 클라이언트는 서버에게 “공격하고 싶습니다”라고 요청합니다. 서버는 공격 거리가 맞는지, 공격 쿨타임이 끝났는지, 플레이어가 살아 있는지 확인합니다. 조건이 맞으면 서버가 공격을 인정합니다. 그리고 그 결과를 다른 클라이언트에게 알려줍니다.

이렇게 해야 치트나 잘못된 상태를 줄일 수 있습니다. 그래서 피시넷을 사용할 때는 항상 “서버가 최종 판단을 한다”는 생각을 기본으로 가져가야 합니다.

챕터 이. 전체 흐름

피시넷의 전체 흐름은 이렇게 이해할 수 있습니다.

첫째, 유저가 키보드나 마우스로 입력합니다.

둘째, 클라이언트는 그 입력을 서버에 보냅니다.

셋째, 서버는 입력이 올바른지 검사합니다.

넷째, 서버는 게임 상태를 바꿉니다.

다섯째, 바뀐 상태나 이벤트를 클라이언트들에게 보냅니다.

여섯째, 클라이언트는 받은 정보를 화면에 보여줍니다.

여기서 상태와 이벤트를 구분해야 합니다.

상태는 계속 유지되는 값입니다. 체력, 점수, 닉네임, 현재 무기, 준비 완료 여부가 상태입니다.

이벤트는 순간적으로 일어나는 일입니다. 총소리, 폭발, 피격 이펙트, 버튼 클릭 결과, 알림 창 표시가 이벤트입니다.

상태는 주로 싱크 바와 싱크 타입으로 동기화합니다. 이벤트는 주로 알피시로 전달합니다.

이 구분을 잘하면 네트워크 코드를 훨씬 깔끔하게 설계할 수 있습니다.

챕터 삼. 네트워크 매니저

피시넷의 중심에는 네트워크 매니저가 있습니다.

네트워크 매니저는 멀티플레이 시스템의 본부입니다. 서버를 시작하고, 클라이언트를 연결하고, 씬을 관리하고, 네트워크 오브젝트를 스폰하고, 시간을 맞추고, 통신 흐름을 관리합니다.

네트워크 매니저 아래에는 여러 매니저가 있습니다.

서버 매니저는 서버 쪽 일을 담당합니다.
클라이언트 매니저는 클라이언트 쪽 일을 담당합니다.
트랜스포트 매니저는 실제 네트워크 데이터 이동을 담당합니다.
타임 매니저는 네트워크 시간과 틱을 담당합니다.
씬 매니저는 멀티플레이 씬 로딩을 담당합니다.
옵저버 매니저는 어떤 클라이언트가 어떤 오브젝트를 볼 수 있는지 담당합니다.
스태티스틱스 매니저는 네트워크 트래픽 같은 통계 정보를 확인할 때 사용합니다.

초보자는 처음에 모든 매니저를 깊게 외울 필요는 없습니다. 먼저 네트워크 매니저가 전체를 관리하고, 나머지 매니저들이 각 분야를 나눠 맡는다고 이해하면 충분합니다.

챕터 사. 네트워크 오브젝트와 네트워크 비헤이비어

피시넷에서 네트워크로 동기화할 오브젝트에는 네트워크 오브젝트가 필요합니다.

그냥 유니티 게임 오브젝트를 만들었다고 해서 자동으로 모든 클라이언트에게 보이는 것은 아닙니다. 네트워크로 존재해야 하는 오브젝트라면 네트워크 오브젝트로 만들어야 합니다.

예를 들어 플레이어 캐릭터, 몬스터, 투사체, 네트워크로 공유되는 문, 점령 지점 같은 것들이 네트워크 오브젝트가 될 수 있습니다.

그다음 중요한 것이 네트워크 비헤이비어입니다.

일반 유니티 스크립트는 모노 비헤이비어를 상속합니다. 피시넷에서 네트워크 기능을 쓰는 스크립트는 네트워크 비헤이비어를 상속합니다.

네트워크 비헤이비어를 사용하면 서버인지, 클라이언트인지, 오너인지, 스폰된 상태인지 같은 네트워크 정보를 확인할 수 있습니다. 또한 서버 알피시, 옵저버스 알피시, 타깃 알피시 같은 통신 기능을 사용할 수 있습니다.

간단히 말하면 네트워크 오브젝트는 네트워크에 존재하는 몸체이고, 네트워크 비헤이비어는 그 몸체 안에서 네트워크 로직을 실행하는 스크립트입니다.

챕터 오. 알피시

알피시는 원격으로 함수를 실행시키는 방식입니다.

피시넷에서는 알피시를 크게 세 가지로 나눠 생각하면 됩니다.

첫째, 서버 알피시.
둘째, 옵저버스 알피시.
셋째, 타깃 알피시.

서버 알피시는 클라이언트에서 서버로 보내는 요청입니다.

플레이어가 공격 버튼을 눌렀습니다. 클라이언트는 서버에게 공격 요청을 보냅니다. 이때 서버 알피시를 사용합니다.

플레이어가 아이템을 먹으려 합니다. 클라이언트는 서버에게 아이템 획득 요청을 보냅니다. 이때도 서버 알피시를 사용합니다.

서버 알피시는 반드시 검증이 필요합니다. 클라이언트가 보낸 값은 믿으면 안 됩니다. 서버는 거리, 상태, 권한, 쿨타임, 체력 같은 조건을 다시 확인해야 합니다.

옵저버스 알피시는 서버에서 여러 관찰자에게 이벤트를 보내는 방식입니다.

예를 들어 폭발 이펙트를 보여주거나, 총소리를 재생하거나, 캐릭터의 피격 애니메이션을 실행할 때 사용할 수 있습니다.

여기서 옵저버란 해당 네트워크 오브젝트를 볼 수 있는 클라이언트를 뜻합니다. 모든 클라이언트가 아니라, 필요한 클라이언트에게만 보내는 것이 중요합니다.

타깃 알피시는 서버에서 특정 클라이언트 한 명에게만 메시지를 보낼 때 사용합니다.

예를 들어 한 플레이어에게만 퀘스트 완료 창을 띄우거나, 한 플레이어에게만 개인 보상 결과를 보여주거나, 특정 클라이언트에게만 화면 흔들림을 적용할 수 있습니다.

정리하면 이렇습니다.

클라이언트에서 서버로 보내면 서버 알피시.
서버에서 여러 관찰자에게 보내면 옵저버스 알피시.
서버에서 한 명에게만 보내면 타깃 알피시.

챕터 육. 싱크 바와 싱크 타입

싱크 바는 서버에서 바뀐 값을 클라이언트에게 자동으로 맞춰주는 기능입니다.

가장 쉬운 예는 체력입니다.

서버에서 플레이어 체력이 백에서 칠십으로 바뀌면, 클라이언트도 그 값을 칠십으로 받습니다. 그래서 화면의 체력 바가 올바르게 표시됩니다.

싱크 바는 단일 값에 잘 맞습니다. 체력, 점수, 닉네임, 팀 번호, 준비 상태, 현재 무기 같은 값이 좋은 예입니다.

하지만 게임에는 단일 값만 있는 것이 아닙니다. 목록이나 사전 형태의 데이터도 있습니다. 이럴 때는 싱크 타입을 사용합니다.

싱크 리스트는 목록을 동기화합니다. 접속자 목록, 인벤토리 목록, 방 참가자 목록에 어울립니다.

싱크 딕셔너리는 키와 값 구조를 동기화합니다. 플레이어별 점수, 아이템별 개수, 팀별 점수에 어울립니다.

싱크 해시 셋은 중복 없는 집합을 동기화합니다. 점령된 지역 목록, 이미 획득한 업적 목록, 활성화된 상태 목록에 어울립니다.

싱크 타이머와 싱크 스톱워치는 시간 관련 값을 동기화할 때 사용합니다. 제한 시간, 쿨타임, 경기 시간처럼 서버와 클라이언트가 같은 시간 감각을 가져야 할 때 도움이 됩니다.

싱크 타입을 사용할 때 가장 중요한 원칙은 서버에서 값을 바꾸는 것입니다. 클라이언트가 직접 값을 바꾸는 구조로 만들면 상태가 꼬일 수 있습니다.

챕터 칠. 브로드캐스트

브로드캐스트는 특정 네트워크 오브젝트에 묶이지 않은 메시지를 보낼 때 사용합니다.

알피시는 보통 네트워크 오브젝트와 네트워크 비헤이비어에 연결된 함수 호출입니다. 반면 브로드캐스트는 구조화된 메시지를 보내는 방식입니다.

예를 들어 채팅 메시지를 생각해보겠습니다. 채팅은 반드시 특정 캐릭터 오브젝트의 함수에 묶일 필요가 없습니다. 클라이언트가 채팅 메시지를 서버에 보내고, 서버가 다시 필요한 클라이언트에게 전달하면 됩니다.

이럴 때 브로드캐스트가 잘 맞습니다.

브로드캐스트는 채팅, 인증, 로비 메시지, 매치메이킹, 전역 알림처럼 특정 오브젝트에 종속되지 않은 통신에 유용합니다.

초보자는 이렇게 구분하면 됩니다.

네트워크 오브젝트의 동작을 호출하고 싶으면 알피시.
오브젝트와 상관없는 메시지를 보내고 싶으면 브로드캐스트.

챕터 팔. 스폰과 디스폰

멀티플레이에서 오브젝트를 생성할 때는 스폰 개념이 중요합니다.

유니티에서 그냥 오브젝트를 생성하는 것과 피시넷에서 네트워크 오브젝트를 스폰하는 것은 다릅니다.

그냥 생성하면 내 컴퓨터에만 생길 수 있습니다.
네트워크 스폰을 하면 서버가 그 오브젝트의 존재를 네트워크 전체에 알려줍니다.

피시넷에서는 네트워크 오브젝트 스폰을 서버 기준으로 처리해야 합니다.

예를 들어 몬스터를 생성한다고 해보겠습니다. 클라이언트가 마음대로 몬스터를 생성하면 다른 클라이언트와 상태가 맞지 않을 수 있습니다. 서버가 몬스터를 스폰하고, 그 결과를 클라이언트들에게 알려야 합니다.

디스폰은 반대로 네트워크 오브젝트를 네트워크에서 제거하는 것입니다. 몬스터가 죽었거나, 투사체가 사라졌거나, 아이템을 획득해서 없어져야 할 때 디스폰합니다.

스폰과 디스폰은 네트워크 오브젝트의 생명 주기를 관리하는 핵심입니다.

챕터 구. 오너십

오너십은 어떤 클라이언트가 어떤 네트워크 오브젝트를 소유하고 있는지를 나타냅니다.

예를 들어 내 플레이어 캐릭터는 보통 내 클라이언트가 오너입니다. 그래서 내 클라이언트는 그 캐릭터에 대한 입력을 보낼 수 있습니다.

하지만 오너라고 해서 모든 것을 마음대로 바꿀 수 있다는 뜻은 아닙니다.

안전한 구조에서는 오너 클라이언트가 입력을 보내고, 서버가 그 입력을 검증합니다. 검증 후 서버가 실제 위치, 체력, 공격 결과 같은 상태를 확정합니다.

오너십은 입력 권한과 관련이 있습니다. 하지만 게임 상태의 최종 결정권은 서버에 두는 것이 좋습니다.

이 원칙을 지키면 치트, 동기화 오류, 상태 불일치를 줄일 수 있습니다.

챕터 십. 옵저버 시스템

옵저버 시스템은 누가 어떤 오브젝트를 볼 수 있는지 정하는 시스템입니다.

멀티플레이 게임에서 모든 오브젝트의 모든 정보를 모든 클라이언트에게 보내면 성능이 나빠집니다.

예를 들어 넓은 월드가 있다고 해보겠습니다. 서울에 있는 플레이어에게 부산에 있는 몬스터의 세부 상태를 계속 보낼 필요는 없습니다. 같은 방에 있지 않은 플레이어에게 다른 방의 세부 정보를 계속 보낼 필요도 없습니다.

옵저버 시스템은 이런 낭비를 줄입니다.

가까운 사람에게만 보냅니다.
같은 씬에 있는 사람에게만 보냅니다.
같은 매치에 있는 사람에게만 보냅니다.
오너에게만 보냅니다.

이런 식으로 필요한 클라이언트에게만 데이터를 보내면 네트워크 트래픽을 줄일 수 있습니다.

초보자는 옵저버 시스템을 “보낼 사람을 고르는 필터”라고 이해하면 됩니다.

챕터 십일. 프레딕션과 보정

네트워크 게임에서는 지연 시간이 있습니다.

플레이어가 이동 키를 눌렀는데 서버 응답을 기다린 뒤 움직이면 조작감이 답답해집니다. 그래서 클라이언트는 먼저 움직였다고 예측할 수 있습니다. 이것을 프레딕션이라고 부릅니다.

프레딕션은 클라이언트가 자기 입력 결과를 미리 보여주는 기술입니다.

하지만 서버의 최종 결과와 클라이언트의 예측이 다를 수 있습니다. 이때 서버 결과에 맞게 다시 조정해야 합니다. 이것이 보정입니다.

프레딕션과 보정은 고급 기능입니다. 처음부터 바로 적용하려고 하면 어렵습니다.

처음에는 서버 알피시, 싱크 바, 옵저버스 알피시로 기본 구조를 만들고, 움직임이 어색하거나 반응성이 부족할 때 프레딕션을 공부하는 것이 좋습니다.

챕터 십이. 처음 만들 때의 추천 순서

처음 피시넷을 배울 때는 작은 예제부터 만드는 것이 좋습니다.

첫 번째 목표는 서버와 클라이언트를 연결하는 것입니다.

두 번째 목표는 플레이어를 스폰하는 것입니다.

세 번째 목표는 플레이어의 체력을 싱크 바로 동기화하는 것입니다.

네 번째 목표는 공격 버튼을 누르면 서버 알피시로 서버에 요청하는 것입니다.

다섯 번째 목표는 서버가 공격을 검증하고 체력을 줄이는 것입니다.

여섯 번째 목표는 피격 이펙트를 옵저버스 알피시로 보여주는 것입니다.

일곱 번째 목표는 한 명에게만 메시지를 보내는 타깃 알피시를 써보는 것입니다.

여덟 번째 목표는 채팅 메시지를 브로드캐스트로 만들어보는 것입니다.

이 순서대로 하면 피시넷의 핵심 통신 방식을 자연스럽게 익힐 수 있습니다.

마무리

피시넷을 처음 배울 때 가장 중요한 것은 용어를 많이 외우는 것이 아닙니다. 흐름을 이해하는 것입니다.

클라이언트는 요청합니다.
서버는 검증합니다.
서버는 상태를 바꿉니다.
클라이언트는 결과를 받습니다.

상태는 싱크 바와 싱크 타입으로 맞춥니다.
이벤트는 알피시로 보냅니다.
오브젝트와 관계없는 메시지는 브로드캐스트로 보냅니다.
네트워크 오브젝트는 서버가 스폰합니다.
오너십은 입력 권한과 관련되지만, 최종 권위는 서버에 둡니다.
옵저버 시스템은 필요한 사람에게만 데이터를 보내기 위한 필터입니다.

이 기본 구조를 이해하면, 피시넷 문서를 읽을 때 훨씬 덜 어렵게 느껴집니다.

처음에는 작은 멀티플레이 예제 하나를 완성하는 것을 목표로 하세요.
서버 접속, 플레이어 스폰, 체력 동기화, 공격 요청, 이펙트 전달까지 만들 수 있다면 피시넷의 핵심은 이미 잡은 것입니다.
